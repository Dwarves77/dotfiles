## 8. Build plan for this module

### The one turn runtime

The new tree keeps ONE turn runtime: `src/core/turn/run-turn.ts`, entered by one CLI (`scripts/turn.mjs --stage <name|all> --mode dry|apply`), that runs an ordered stage plan, reads the build-mode gate once, records every stage's outcome in the run ledger in the same process, and triggers its downstream stage itself (rule 17). It replaces the eleven deleted workflows' graph, the seven runtimes in this scope, the six emitters and the delivery shell (P1-12's files), and every local-directory resume read.

Stages, in order (each a module under `src/core/turn/stages/`, each with a pure planner and a pure shaper over injected clients):

1. `sweep`: the four walkers plus `research` (from run-source-sweep.mjs, research-sweep.mjs). Under build mode (scrape_cadence off) the stage runs dry (INV-051); this is expected, not a defect (CLAUDE.md rule 16).
2. `change`: gate read, the check in process, reconcile once, drain change-sweep staged updates (from run-change-detection.mjs; route logic P1-05).
3. `capture`: the first-fetch drain (from run-fetch-drain.mjs), through P1-07's capture worker.
4. `intake`: ledger consume by session verdict, promote under the cap, record-grade mint through P1-14 (from run-ledger-consume.mjs).
5. `connect`: the flywheel over the slice the intake stage just minted (from run-population-flywheel.mjs), plus the unscoped entry for a brief-apply batch.
6. `propagate`: outbox drain, questions-on-change, signposts (from run-propagation-drain.mjs).
7. `briefs`: the session-authored batch kinds (theme briefs from this scope; record briefs, need URLs, question answers, extraction output from P1-12), each an export half and an apply half over the one batch-validator pattern.

Reconciliation with P1-08 (harness.md, on master): P1-08 plans `runFamily(name, input)` with a `FAMILIES` table naming each family's owning module and downstream families, and assigns ledger-consume to P1-03/04, propagation and downstream-chain to P1-09/10, and change-detection and fetch-drain to P1-12..15 (harness.md:312-335). This register does not contradict that: each stage above IS one family run through `runFamily`, and the turn runtime is the ordered plan over those families (the `downstream` names made executable in one process), not a second frame.
