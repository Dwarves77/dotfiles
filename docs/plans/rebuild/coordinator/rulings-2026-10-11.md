## 2026-10-16 (later): the member-page navigation loop, cause and ruling

- Symptom: parity runs 38945718256, 38948000046 (PR 20), 38947663046 (PR 21), 38944235505 (PR 19): every signed-in route
  navigates about once a second until the screenshot times out; 4,898 identity 429s in one run; the operator reported the
  same loop recurring in the old build and ruled "the exact cause by looking at code and not guessing".
- Cause [CONFIRMED by code]: AuthProvider.tsx:96 reloads the document on SIGNED_IN when no session user was recorded yet
  (identity-loader.ts:35, shouldReloadOnSignIn). @supabase/auth-js 2.118.0 GoTrueClient.js emits SIGNED_IN from
  _recoverAndRefresh (line 4167, inside _initialize) to every subscriber already registered, and onAuthStateChange (3633)
  registers the subscriber synchronously but emits INITIAL_SESSION only after initializePromise (3654). The browser client
  singleton is first constructed in the same expression that subscribes (AuthProvider.tsx:90), so on every fresh load
  with a stored session SIGNED_IN precedes INITIAL_SESSION, the gate sees `before === null`, and the page reloads itself.
  The null-workspace redirect (AppShell.tsx:44 to /workspace/new) is a one-hop redirect to a chromeless 404 and was not
  the loop; the parity account has an org (bootstrap reached the roster).
- Ruling: no document reload from any auth event. Cross-tab sign-in re-fetches identity in place (loader rearm) only when
  identity had resolved with no user; SIGNED_OUT navigates to /login only from a route that requires auth and never from
  /login itself (route-policy's classification, no second list). Red-first tests replay the real event order.
  Mechanism that catches the class: the parity capture records main-frame navigations per route (P2-CI2); a route with
  more than three navigations fails the capture.
- Assigned: P2-02c (fix and tests), P2-CI2 (navigation ceiling in capture.mjs).
- Corroborated by run 38949606622 (P2-CI2 diagnostics): every member route navigated 628 to 690 times to ONE path (its own),
  the first non-2xx being the page's 404 frame; a self-reload, as the code chain predicts. [CONFIRMED]
- Second finding from the same run [CONFIRMED]: signed-out routes received 429 from /api/auth/identity because the job's
  smoke steps load pages from one IP in the minute before the capture, and a per-IP 60/min window on identity also breaks
  an office behind one NAT address. Ruling (retracts "the IP limiter stays" in the P2-02c message): identity answers an
  anonymous request without the limiter or a database call; a request with a session is limited per user id from the
