## Findings against the operator's three concerns

**1. Tools built but unused or duplicated.**
- `attach-found-sources.mjs` and `tier-opinions.mjs` (W3) are both fully built, wired into `maintenance.yml`, unit-tested — and never dispatched in apply mode. [CONFIRMED] `source_tier_opinions` = 0 rows; no `attach-found-sources` run artifact anywhere in the tree. This is exactly the "built, dormant" failure mode plan §0 exists to forbid, still present at `1e6d9e8b`.
- `write-statutory.mjs` is built and wired but has no real input: the one rows-file present in the tree is explicitly self-labeled a non-production fixture, and it sits at a different path than the one `propagation-drain.yml` looks for (`scripts/_worklists/...` vs `scripts/propagation/fixtures/...`), so even a coordinator who found the fixture and mistakenly tried to use it would need to relocate it first. [CONFIRMED] `statutory_computations` = 0 rows.
- `backfill-derivation-edges.mjs` vs `backfill-lineage-edges.mjs`: two similarly-named backfill scripts coexist by design (per `maintenance.yml`'s own comment distinguishing them), but this audit could not confirm from content this session that they are genuinely non-duplicative — flagged `[HYPOTHESIS]`, not asserted as either duplicate or distinct with confidence.

**2. Flywheel and harness gaps.**
- The propagation harness family (`scripts/harness-runs/propagation/`) is real and has produced 4 run artifacts, the most recent (`propagation-run-004`) a genuine apply with a measured effect (8 values recomputed). The harness convention itself is followed correctly here.
- The gap is upstream of the harness: `derived_values` (22 rows) and `derivation_edges` (24 rows) are tiny relative to the corpus (2,537+ intelligence items, 2,778 propagation events). The drain and its harness are working correctly on a near-empty DAG; the DAG itself is starved because DAG-authorship-at-write-time only covers two producer chokepoints (carbon intensity, automate-vs-hire), and the historical backfill bridging everything written before those chokepoints existed has not reached its own documented completion signal (two consecutive zero-candidate runs).
- `maintenance.yml`, which holds `attach-found-sources`, `tier-opinions`, `derive-obligations`, `tag-proposals`, `tag-ratification`, and `institution-canonicalize`, has **no `workflow_run` trigger at all** [CONFIRMED by grep: only `propagation-drain.yml` and `population-turn.yml` carry `workflow_run:` blocks; `maintenance.yml` does not]. Every step in that file is `workflow_dispatch`-only. This is a harness/chaining gap distinct from W1.4's chaining (source-sweep → ledger-consume → population-turn → [via producers] → propagation-drain), which does exist and is real per this session's reading of the three chained workflow files.

**3. Runtimes that don't trigger their downstream (rule 17).**
- **[CONFIRMED, most consequential finding of this audit]** `apply-mint-batch.mjs` — the actual write path population-turn uses for the record-grade mint volume (dispatch ledger: apply runs #35–38 minted 120+103+89+104 = 416 items on 2026-09-04 alone) — contains this self-documented admission in its own header: *"One consequence, named honestly: mint-item.ts's rule-16 post-insert participation (connection discovery + forward-event extraction, both run unconditionally inside that chokepoint) does NOT run here... this script's job ends at 'the item exists, is grounded, and its provenance verdict is recorded.'"* This is a direct, self-admitted rule-17 violation on the highest-volume mint path in the system: hundreds of record-grade items have been minted with no connection discovery and no forward-event extraction run against them at all, deferred to "a different turn" that this audit found no evidence of ever having been dispatched for those specific batches.
- By contrast, `mint-item.ts` (the single-item, real-time chokepoint) **does** correctly chain connection discovery (rule 16a, ≤12 edges) and forward-event extraction (rule 16b) inside the same call, in the same transaction pattern the spec calls for. The violation is specific to the batch/population path, not universal.
- Neither mint path (batch or single-item) triggers obligation derivation, tag proposals/ratification, or DAG authorship in the same motion. `derive-obligations`, `tag-proposals`, and `tag-ratification` are separate `maintenance.yml` steps with no automatic chaining from population-turn (see finding 2 above) — every dispatch-ledger entry for these three steps shows `run_id: "unknown"`, consistent with hand dispatch, not automatic chaining.
- The propagation drain **is** correctly chained off "Data producers" completing (`propagation-drain.yml`'s `workflow_run` block), and this chain is honest about its own limits: it explicitly does not honor `POPULATION_PAUSED` because draining an already-queued outbox is a different loop from new minting, a distinction this audit's reading of the workflow file confirms is applied correctly, not merely asserted.
