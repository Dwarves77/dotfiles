**007_full_brief.sql** — DEFECT (high confidence). `CREATE OR REPLACE FUNCTION get_workspace_intelligence(p_org_id UUID)` here defines a 28-column `RETURNS TABLE`, differing in count/order/content from 006_multi_tenant.sql's 44-column version of the *same* function name+signature (drops `workspace_notes`, `workspace_tags`, `priority_override`, `workspace_archive_reason/note`, `archive_reason`, `archive_note`, `archived_date`, `replaced_by`, `version_history`, `created_at`, `updated_at`; adds `full_brief` at a different position). Postgres's `CREATE OR REPLACE FUNCTION` cannot change a `RETURNS TABLE` shape without a prior `DROP FUNCTION` — it raises 42P13 ("cannot change return type of existing function", HINT "Use DROP FUNCTION ... first"). This exact error/hint text is corroborated verbatim in migration 272 (outside lane, read for corroboration) for a structurally identical situation, and 272 states explicitly "CREATE OR REPLACE can change a function's BODY but never its RETURNS TABLE shape." Concrete failure scenario: if 007_full_brief.sql replays after 006_multi_tenant.sql (numeric/lexical order — "007" > "006"), the migration should abort at this `CREATE OR REPLACE FUNCTION` statement with 42P13, and (being wrapped in its own transaction) the rest of 007_full_brief.sql would roll back with it. Later migrations in this lane (077, and per grep: 117, 120) explicitly `DROP FUNCTION IF EXISTS get_workspace_intelligence(...)` before recreating — the established remediation for this exact function, consistent with the hypothesis that 007's original apply hit exactly this error and was subsequently patched by hand or via a later drop+recreate. I did not check the migration-history/ledger table for which version is actually recorded as applied; I can only report the static SQL contradiction.
