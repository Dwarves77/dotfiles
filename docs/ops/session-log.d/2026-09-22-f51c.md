## 2026-09-22, lane F51c: check 5 measures concurrent editing, not serial touches by one owner

The lane F51b raw-count definition for F51 check 5 (master touches + this range, threshold 3) still
refused three genuinely serial cases (all [CONFIRMED] in the session log, 2026-09-19 to 2026-09-21): the
lane-briefs README (three serial coordinator docs PRs), the ADR-031 loop-id resolver chain (lanes M3,
M3b, M4, M6b, each cut after the previous merged), and FactCard.tsx's part lanes (parts 1, 2, c, d, each
cut after the previous merged). In every case the lane rebased clean and no concurrent editor existed.
"Touched 3+ times" does not distinguish one owner editing a file serially from two lanes genuinely
editing the same file while both are open, which is the harm plan 6.8 names (a conflict on rebase).

### What changed

Scope: `fsi-app/.discipline/fitness/functions/F51-no-shared-append.mjs` (header comment + check 5 only)
and its sibling test file, per the brief.

- New concurrency definition: a prior commit T on `origin/master` counts against a lane's range ONLY IF
  the lane's branch was already open while T merged, i.e. T is NOT an ancestor of the lane's fork point
  with `origin/master` (`resolveForkPoint` + `classifyConcurrency`). A commit that IS an ancestor of the
  fork point is SERIAL and never counts, however many there are.
- `resolveForkPoint`: locally, `merge-base(origin/master, HEAD)`, measured before any rebase (same
  command `resolveRange`'s local case already uses). In CI, once a queue has rebased the branch, that
  plain merge-base always reads as "just now", so the original fork point is instead read from the PR's
  own first commit's parent (`git rev-list --reverse base..head | head -1`, then `<sha>^`), per the
  brief's exact recipe. This repo's real CI sets `BASE_REF`/`PR_HEAD` (`.github/workflows/discipline.yml`,
  matching `resolveRange`'s own convention), not the generic `GITHUB_BASE_REF` the brief names;
  `resolveForkPoint` honours both names.
- `evaluateConcurrencyViolations` replaces `evaluateHotspotViolations` as check 5's violation core.
  Violation only on a genuinely concurrent prior touch (entry-dir/allowlist/existsCheck exclusions
  unchanged).
- Deleted the seven `HOTSPOT_ALLOWLIST` entries that existed only for serial single-owner work (the
  README, the three loop-id-resolver files, `loop-manifest.mjs`, and the two FactCard part files); kept
  the six coordinator-only-by-contract entries. A new "LIVE-TREE PROOF" test re-runs the concurrency
  definition against the real repo history with the allowlist emptied and confirms all seven clear on
  their own (brief item 3's required verification).
- The standing hotspot count (raw touch count, printed every run for observability) is unchanged: same
  window, same anchor, same threshold 3.
