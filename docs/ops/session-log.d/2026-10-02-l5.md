## UX compliance (lane contract, required section)

All three are read-only rail additions; none introduces a new async action beyond what the existing page already fetches (the assessment prop is already resolved server-side before this surface renders).

- **DissentPanel**: primary goal - let the reader see whether an assessment rests on sources that disagree or vary in standing, without having to infer it from a hidden number. Path: zero steps (renders on page load with the rest of the rail). No primary action (read-only). Feedback state for the absence case: a legible one-sentence absence note ("No dissent recorded for this finding...") - never a blank gap, never a spinner.
- **SignpostList**: primary goal - show what machine-watchable trigger would change this assessment's horizon. Path: zero steps. No primary action. Feedback state: "No signposts watched yet for this finding..." - distinct wording from DissentPanel's absence, so the two cards are never confused for one blank state repeated twice.
- **AssessmentHistoryLedger**: primary goal - let the reader see this assessment's record is append-only and was not silently rewritten. Path: zero steps. No primary action. Feedback states: "No assessment history yet..." (no assessment at all) vs "No prior version recorded yet - this is the first scored assessment..." (an assessment exists, no supersession yet) - two distinct, both legible, honest states, never collapsed into one "last updated" line (the spec's own named anti-pattern).

Every interactive target: none of the three introduce a click target (pure read-only rendering); law 2's floor does not apply to any new control. Law-16 (pattern consistency): every title goes through the shared `SectionHeading` (Anton, `data-guard-display="card-title"`), matching `ResearchAssessmentCard`'s SIBLING cards' visual family even though `ResearchAssessmentCard` itself (PR #887's file, not touched) uses a bespoke header predating this convention - logged as an observation, not a fix I am authorized to make to that file.
