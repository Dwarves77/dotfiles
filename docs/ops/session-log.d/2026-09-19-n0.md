**Amendment 1 item 4 (the real defect I reproduced before writing any code).** From a subdirectory,
`git diff <range> -- <path>` resolves a repo-relative pathspec relative to the spawned process's own
cwd, not the repository root, so the diff for a real path silently comes back empty. I reproduced this
directly with a throwaway repo (no code) before touching anything: from a `sub/` directory, `git diff
origin/master..HEAD -- docs/ops/session-log.d/2026-09-19-n0.md` returned nothing; from the repo root,
the same command returned the real diff. This is exactly what refused lane W10-A on 2026-09-19 (docs/ops/
HANDOFF-2026-09-19-addendum.md section 2). The fix: every git call in `change-range.mjs` first resolves
its own repository top level (`git rev-parse --show-toplevel`, anchored at the module's own file
location by default, never at `process.cwd()`), then spawns the real git command there. `gitChangedFiles`
and `gitDiffLinesForPath` now give the same answer from a subdirectory as from the root, both in a
hermetic fixture test and against the real reproduction above.

`memory-gate.mjs` now imports `gitChangedFiles`/`gitDiffLinesForPath` from the module and its private
copies (the `git()` helper, its own `gitChangedFiles`, its own `gitDiffLinesForPath`) are deleted; its
CLI contract and pure functions (`classifyChanged`, `memoryGateVerdict`, `uxGateVerdict`,
`memoryDiffPaths`, `gitMemoryDiffLines`) are unchanged. `F45-duplicate-code.mjs`'s `changedFiles()` is
now `resolveRange` + `gitChangedFiles` + `gitWorkingTreeFiles`, same result set as before (local
merge-base plus the working tree's own modified/untracked files); `DUPLICATED_LINES_CEILING`, the clone
detector and the failure messages are untouched, per Amendment 1 item 3 (the ceiling line is forbidden
to me this lane; the measured count did not move, see Verification below).
