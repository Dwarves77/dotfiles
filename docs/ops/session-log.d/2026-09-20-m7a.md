### Correction, 2026-09-21 (lane M7a FIX): Vercel function size, cause, fix, before/after

**The failure.** Vercel's build log for PR #765 refused the deploy: `The Vercel Function
"api/admin/statutory-rows" is 252.76mb uncompressed which exceeds the maximum uncompressed size limit of
250mb.` Every repo-side check above had passed (tsc, tests, fitness, rendering guard, CI `next build`) ,
none of them measure a route's traced function size, so the defect shipped past all of them.

**Measured cause** (`.next/server/app/api/admin/statutory-rows/route.js.nft.json`, summed on-disk bytes of
every traced file): **250.63 MB, 3749 files**, with the top 15 largest files ALL under
`fsi-app/scripts/_snapshots/` , historical `census-rows.json`/`census-rows.apply-ready.json` population-run
artifacts, 5-14 MB each. The sibling route `/api/admin/attention` traced at 1.47 MB, 64 files , three
orders of magnitude smaller, confirming this was not a systemic tracing problem.

Root cause, traced by hand: `logic.mjs` imported `parseRow`/`writeOneRow` from
`scripts/propagation/write-statutory.mjs`, which imports `scripts/lib/db.mjs` for `guardedInsert`/`readAll`.
`db.mjs`'s guarded-write path snapshots every write for reversibility (rule 015) via `snapDir()` =
`resolve(dirname(fileURLToPath(import.meta.url)), "..", "_snapshots")` , a path that is STATICALLY
resolvable at build time (it depends only on the module's own location, never a runtime argument). Next's
output-file tracer (`@vercel/nft`) resolved that expression and pulled the ENTIRE
`fsi-app/scripts/_snapshots/` directory into the trace, because merely IMPORTING anything from `db.mjs`
drags in that file's whole static fs surface for nft's analysis , not just the one export (`readAll`) the
route actually used. This is exactly hypothesis (a) in the fix dispatch, confirmed by direct measurement,
not inferred.

**The fix (option 2a only , 2b/outputFileTracingExcludes explicitly withdrawn by operator ruling "no
workarounds").** Extracted the ONE pure home for this logic: `fsi-app/src/lib/propagation/statutory-rows.ts`
, row-parsing (`parseRow`), rows-file validation (`validateSourceBlock`/`validateRow`/`validateRowsFile`),
and the single-row write/entity-mint (`writeOneRow`/`resolveOrMintEntity`), none of which import
`scripts/lib/db.mjs`, `node:fs`, `node:path`, or build any dynamic path , no top-level side effects, no
`process.cwd()`. `writeOneRow`/`resolveOrMintEntity` take an injected Supabase client and default to a
PLAIN, fs-free insert (no snapshot); a caller that wants the guarded/snapshot/cite discipline (a real CLI
`--apply` run, where a local-disk audit trail makes sense) injects `scripts/lib/db.mjs`'s `guardedInsert`/
`readAll` explicitly. `scripts/propagation/write-statutory.mjs` and
`scripts/propagation/validate-statutory-rows-file.mjs` now import from this one home and keep only their
CLI concerns (args, env loading, client creation, the guarded-insert wiring for a real apply run); neither
re-implements row parsing, validation, or the write. `src/app/api/admin/statutory-rows/logic.mjs` imports
directly from the pure home, not from either CLI script , the route no longer touches `db.mjs` at all,
so nft has nothing fs-static to walk from this route's import graph.

**Behavior note (deliberate, not incidental).** The API route's writes now use the plain insert (no
snapshot file), where before they used `guardedInsert` by way of `write-statutory.mjs`'s default. This is
judged a CORRECTION, not a regression: a Vercel serverless function's filesystem is ephemeral/read-only
outside `/tmp`, so `db.mjs`'s `appendFileSync`-to-`scripts/_snapshots/` snapshot pattern was never a
durable audit trail in this route's actual deployed context , it is a CLI/local-disk convention that does
not survive an API route's process boundary regardless of import wiring. The CLI's own `--apply` path is
unchanged and keeps the guarded/snapshotted write.

`logic.test.mjs`'s attack-form assertions were updated (not removed) to match the new one-home shape: the
route imports `validateRowsFile`/`parseRow`/`writeOneRow` from `src/lib/propagation/statutory-rows.ts` and
explicitly must NOT import either CLI script; `write-statutory.mjs` and `validate-statutory-rows-file.mjs`
are asserted (by reading their source) to import the pure functions from the same home rather than
defining their own. A fixture that re-implements validation in the route OR in a CLI script still fails.

**Measured before/after** (same trace file, same method):
- Before: **250.63 MB, 3749 files** (top offenders: `scripts/_snapshots/*/census-rows*.json`).
- After: **1.47 MB, 63 files** (top offender: `next-server/app-page-turbo.runtime.prod.js`, 0.49 MB , an
  ordinary Next.js runtime chunk).
- Sibling baseline (`/api/admin/attention`): **1.47 MB, 64 files** , after-fix and baseline now match to
  the same order of magnitude, as required.

Verification: `npx tsc --noEmit` exit 0, no output. `node --test` on
`src/app/api/admin/statutory-rows/logic.test.mjs`, `scripts/propagation/write-statutory.test.mjs`,
`scripts/propagation/validate-statutory-rows-file.test.mjs`, and
`scripts/_worklists/statutory-fueleu-annex-iv-2026-09-05.test.mjs` (which also imports from
`write-statutory.mjs`): 33 tests, 33 pass, 0 fail, unmodified except the two attack-form assertions named
above. `node .discipline/fitness/runner.mjs --function=F13/F25/F45/F51`: all PASS, 0 violations (F45 exact
parity 6121/6121; F51 does not flag any touched file).

**The lesson.** A route that imports from `fsi-app/scripts/` must have its traced function size measured
(`.next/server/.../route.js.nft.json`, sum the `files` array's on-disk bytes) BEFORE push, not discovered
at Vercel's build gate , none of tsc, unit tests, fitness, or the rendering guard measure a route's
serverless-function bundle size, and a CLI script's fs-backed helper (however well-governed for its own
context) can silently balloon an API route's trace just by being imported, whether or not the route ever
calls the fs-touching function at runtime.
