## Addendum, 2026-09-30: `[CONFIRMED]` cause and fix, from the coordinator's live SELECT

The coordinator ran the SELECT this lane's own "Open items" asked for (no DB credentials in this
worktree) and passed the result back, 2026-09-30. Across `intelligence_item_sections` joined to
`market_signal`/`initiative` items: 631 rows start with `"["` or `"{"`, 430 `section_key='record_facts'`
(430 distinct items), 201 `section_key='identity'` (201 items). Sample rows: `record_facts` begins
`"[action_now] No verbatim action now statement was located in the captured source text for this
record-grade it..."`, `identity` begins `"[title] The captured source's own text carries this item's
title verbatim: «13.2.2020 EN Official Journal of t..."`.

**`[REFUTED]` as JSON**, confirming this session's earlier code-review verdict on `JSON.stringify`.
**`[CONFIRMED]` as the operator's "raw text dump mid-page"**: these are `record_facts.mjs`'s own
`[slot_key] <claim text>` claim-line format (`extractSlotFact`/`extractIdentityFact`,
`src/lib/intake/record-facts.mjs`, read outside this lane's write set for tracing only, not edited),
the exact format `src/lib/agent/parse-record-sections.ts` (also outside the write set, read only) exists
to turn into labelled fields, not raw prose.

**Trace (the coordinator's assignment): how do these render on the market detail page.**
`MarketSignalDetailSurface.tsx`'s Summary section has two branches on `isRecord = r.itemGrade ===
"record"`:
- `isRecord` true: `RecordGradeSections` -> `parseRecordSections(sections, claimTiers)` ->
  `RecordFactsBody`/`RecordFactCard` (`src/components/detail/primitives.tsx`, outside the write set,
  read only). A FACT row (e.g. the `[title]` sample) renders correctly as a labelled `FactCard`
  (`deriveRecordFactCardModel`), never as raw text. A GAP row (e.g. the `[action_now]` sample) is
  parsed into `parsed.gaps` but `RecordGradeSections` never passes `gaps` to `RecordFactsBody` at all,
  so GAP claims render NOWHERE in Summary depth today (a second, smaller finding, not this workstream's
  scope, noted below).
- Unconditionally, regardless of `isRecord`: `{depth === "full" && r.fullBrief && <GfmSection
  markdown={r.fullBrief} />}`. `buildRecordFullBrief` (`record-facts.mjs`) re-serializes the SAME claim
  rows as bare `- [slot_key] ...` markdown bullets under `## Verbatim facts` / `## Not stated in the
  captured source` headings, written to be Gate A's digit-free provenance corpus, never end-reader
  prose (its own file header says so). `GfmSection` (remark-gfm) renders that markdown as a literal
  bulleted list, both sample lines verbatim, bracket prefix and all. **This is the `[CONFIRMED]` dump**:
  a market detail reader (or a crawler) who opens a record-grade item and switches Summary depth to
  "Full brief" sees the exact same facts twice, once correctly labelled (above) and once as raw
  `[slot_key] ...` machine text (this block), on 631 sections across 631 items.

**Fix (class-level, in write set):** `MarketSignalDetailSurface.tsx`, gated the Full-brief `GfmSection`
render behind `!isRecord`. Record-grade items never open the raw path: `RecordGradeSections` is already
their complete Full-brief view (`parseRecordSections` reads the identical `sections` rows
`buildRecordFullBrief` re-serializes), so nothing is lost, only the duplicate raw block is removed.
Comment left in the code names the mechanism, the `[CONFIRMED]` evidence, and points to this file.

**Renderer files outside this lane's write set** (`src/app/market/[slug]/**`,
`MarketSignalDetailSurface.tsx`, `src/lib/market/**`): `src/lib/agent/parse-record-sections.ts`,
`src/components/detail/primitives.tsx`, `src/lib/intake/record-facts.mjs`. All three were READ (to
trace the mechanism) but not edited, per the coordinator's instruction to name them if the renderer
lived outside the write set. None needed editing for this fix: the defect and its fix are both fully
inside `MarketSignalDetailSurface.tsx`.

**Not this lane's scope, flagged for a follow-up (rule 13):** `RecordGradeSections` never surfaces GAP
claims at all (Summary depth silently drops them; `parseRecordSections`'s own doc comment says
`slotFieldCount` exists to drive an "N of M record fields not stated" honesty line, but Market's
`RecordGradeSections` never builds one). `RegulationDetailSurface.tsx` carries the SAME unguarded
`{depth === "full" && r.fullBrief && <GfmSection .../>}` pattern at its own line 385 (read for
comparison only, not edited, out of write set), same class of defect, unconfirmed whether regulation
items are record-grade in practice at the same rate; a future lane should check.
