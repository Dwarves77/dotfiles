### UX compliance (w10-factcard)

- Screen/block changed: FactCard (`src/components/ui/FactCard.tsx`), a shared card part mounted
  inside the four detail surfaces' sections and inside `RecordFactCard`. Not a full screen; a
  reusable content block.
- Primary goal: let the reader tell apart, at a glance, what KIND of claim a card is (an action
  required, a legal question, a deadline/target/scope/penalty/definition fact, or the pipeline's own
  inference) and reach its source in one click.
- Path: reader opens a detail page -> scrolls to a section -> reads the kind band (what this is) ->
  reads the figure lead and claim (the fact) -> clicks the provenance link (verifies it). No
  interaction is required to reach the information; the only actionable control is the provenance
  link.
- One primary action: the provenance link (`Open source`-equivalent, now the host name + a NE
  arrow), styled as the only inline `<a>` in the card. Everything else is read-only text.
- Feedback state: the link is a normal `target="_blank"` navigation (browser-native feedback, no
  async state to acknowledge). No loading/error/success state applies to this component: it renders
  synchronously from already-fetched section content passed in as a prop; there is no in-component
  async action.
- This is a style-and-structure swap for an existing part (FactCard already existed, was already
  mounted on every named consumer, and the record-facts data itself did not change) with one real
  behavior change: the card's kind is now derived and shown (v1 showed only three generic labels
  "Fact"/"Legal confirmation required"/an eyebrow humanized label; v2 shows the pipeline's actual
  nine-word kind vocabulary), and the provenance link text changed from the fixed string "Open
  source" to the linked host name. Said honestly per the contract's "be truthful about scope" rule:
  this is not a pure style swap, it changes what information the reader sees, but it does not add or
  remove any user-initiated action.
- Amendment 1 pass addendum: the `RECORD_SLOT_KIND` table (ruling B.3) is a further, small reader-
  visible change on the same part - a record-grade row whose slot key is `effective_date`,
  `primary_deadline`, `due_date`, `penalty_summary` or `jurisdictional_scope` now shows DEADLINE,
  PENALTY or SCOPE in the kind band instead of always SCOPE. No new interaction, no new control; the
  primary goal, path, primary action and feedback state above are unchanged. `data-part`/`data-kind`
  are non-visual DOM attributes with no reader-facing effect.

### Correction (2026-09-20, PR #763 CI): rendering-guard placeholder-literal false positive

**The failure.** The "Rendering guard" CI job on PR #763 failed six specs, all the same shape:
`detail-regulations:record-grade-facts-and-connections@375` and `@1280`, and
`detail-research:record-grade-facts` / `detail-market:record-grade-facts` at both widths -
`placeholder literal rendered - DEADLINE`.

**The cause.** [CONFIRMED, by reading `source-entry-filter.mjs` and `fact-card-model.ts`.]
`source-entry-filter.mjs`'s `HEADER_LITERALS` set lists `"deadline"` (lowercased) as a section 8
obligations-table HEADER literal - an older, unrelated defect class (F-1, 2026-07-09: a parsed
table's HEADER row rendering as fabricated DATA). `isPlaceholderText` lowercases and exact-matches
against that set. FactCard v2's kind band (this lane, artboard 21c) renders the kind word verbatim
in a `<p>`, and `DEADLINE` is one of the operator's nine FIXED `FACT_CARD_KINDS` (parts-brief-
2026-09-18.md section 2.1) - a real, deliberate vocabulary word for this band, not an unfilled
slot. The two "deadline" meanings collided: the detector could not tell a kind-band label from a
placeholder header echo, because nothing in the DOM told it which one it was looking at.

**Which of 2a/2b, and why.** 2b - the detector cannot tell a kind-band label from an unfilled slot;
the card is correct as designed. Evidence: `FACT_CARD_KINDS` in `fact-card-model.ts` is the
operator-ratified fixed vocabulary the parts brief specifies by name, including `DEADLINE`; the
card renders exactly that word in exactly the kind band the artboard specifies. There is no "real
date" fixture expectation this collides with - the record-grade fixtures' fact spans are separate
claim text, not the kind word itself.

**The fix.** `src/components/ui/FactCard.tsx`'s kind-word `<p>` now also carries
`data-part-slot="kind-word"` (alongside its existing `data-guard-title`), inside the card's
existing `data-part="fact-card"` root. `.discipline/rendering/smoke/harness.mjs`'s `measureGuard`
gained a narrow, attacked exemption (`isDeclaredKindWord`, same shape as the file's existing
`isDeclaredAbsence` exemption for the shared Absence part): a scanned cell is exempt from the
placeholder-literal check ONLY when it sits inside a `data-part-slot="kind-word"` element, that
element sits inside a `data-part="fact-card"` ancestor, AND the slot's own text is one of the nine
values in `FACT_CARD_KINDS` (imported from `fact-card-model.ts`, not a second hand-copied list -
Node 24's native `.ts` type-stripping, same precedent as `assertions.test.mjs`'s existing
`relative-time-format.ts` import). Attack tests in the new `harness.npmtest.mjs` (5 tests, all
green): (i) the bare word in a plain element still fails; (ii) the kind word in a marked kind band
inside a real fact card passes, for all nine kinds, not just DEADLINE; (iii) a marked kind band
holding a non-vocabulary word (`TBD`) still fails; (iv) the marker outside a `data-part="fact-card"`
ancestor still fails; (v) the check resolves correctly when called on a descendant of the slot
element, matching how the real DOM scan calls it. `FactCard.npmtest.mjs` gained a structural
assertion that the component actually carries `data-part-slot="kind-word"`.
