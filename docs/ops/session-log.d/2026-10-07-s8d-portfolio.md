### Accomplished
- Migration `362_portfolios.sql` (NOT APPLIED): `portfolios` (org-owned, name unique per org case-insensitively, `UNIQUE (id, org_id)`) and `portfolio_members` (`item` by `intelligence_items.id`, `corridor` and `entity` by `entities.entity_id`; one target matching the kind by CHECK; composite FK `(portfolio_id, org_id)` pins a member to its portfolio's org; partial unique indexes make an add the same record from any surface). RLS on both tables through `user_belongs_to_org(org_id)`; INSERT binds the author to `auth.uid()`; a signed-in user can UPDATE only `portfolios.name` (column grant) and cannot UPDATE a member at all; anon has nothing. Caps by trigger: 100 portfolios per org, 500 members per portfolio, so every read is bounded. A self-check DO block attacks the policies as two real orgs' members in a rolled-back sub-transaction (cross-org read, create, member injection under either org id, forged author, rename, delete, empty, org_id rewrite, member edit) and skips with a NOTICE when fewer than two orgs with disjoint members exist.
- Rules in `src/lib/portfolio/portfolio-core.mjs` (plain ESM, injected client): name and member parsing, list, create (a duplicate name returns the existing record), rename, delete, add and remove a member, and `computeRollup`. Every statement is filtered by the org the route resolves from `org_memberships`; another org's portfolio id is a 404 that writes nothing. An item is addable only when held (verified, not archived); an entity only when active (a merged one resolves to its survivor, a retired one is refused).
- Roll-ups are computed per request and stored nowhere: per surface, per priority, nearest binding date, the weakest origin class (`weakestOriginClass`), and the held-over-total denominator with the not-held member ids named. They are the spec's own aggregate rules (section 8 assertions 9 and 13, section 3.6), not new ones.
- API under `/api/workspace/portfolios`: `GET` and `POST` (list, create); `[id]` `GET` (hydrated view with roll-ups), `PATCH` (rename), `DELETE`; `[id]/members` `POST` and `DELETE`. Thin route files over `route-support.ts`; reads in `read.ts`.

### Decisions
- Members are three kinds (item, corridor, entity) as the brief says; a corridor is an entity whose id is `cl:corridor:*`, so `entity` excludes corridors by CHECK and an id has exactly one kind.
- Team-shareable, as spec 00 section 5 and workspace tags: every org member can read, create, rename and delete. "Owned" is recorded as `created_by`.
- The roll-up set is the spec's aggregate rules (denominator, weakest class, per surface, nearest date). Spec 00 section 5 names no list of roll-ups, so I took the minimum those rules require and invented nothing else.
- Entity rows link to `/search?q=<label>` because the entity canonical page (assertion 3) does not exist; they carry no band or figure of their own (the Absence convention), since an entity has no urgency band.
- The RLS attacks run in the migration's own self-check (the 356 pattern) and are pinned statically in `362_portfolios.test.mjs`; the 311 lesson (a migration cannot mint a `profiles` row) is why the fixtures are real orgs and real members.

### UX compliance
- Screen: /dashboard/portfolio. Primary goal: open a portfolio or make one. Path: one click on a name; to create, type a name and press Create (two steps), and the new portfolio opens. Primary action: Create portfolio (the only primary button). Feedback: the button reads "Creating..." while in flight and is disabled for a blank name; a failure shows an inline banner with the typed name kept; success navigates to the new portfolio; empty, signed-out and unavailable each have their own note naming the next step. Targets: the name input, button and each portfolio link are 44px tall; measured at 375, 768, 1024 and 1280 with no target below the floor.
- Screen: /dashboard/portfolio/[id]. Primary goal: see what the portfolio holds and what needs attention first. Path: the page opens on the roll-ups and the groups, nearest date first, zero steps to read; one tap to open an item. Primary action: Add (search card); remove, rename and delete are quieter. Feedback: Adding, Saving, Deleting and Removing labels while in flight; a failure shows an inline banner and leaves the search, the results and the typed name where they were; delete asks "Yes, delete portfolio" or "Keep it" first and says the items themselves stay; an empty portfolio ends on a note that names the next step; the not-held note says they are counted in the total and left out of every figure.
