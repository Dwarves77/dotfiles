## 2026-09-22, lane G4: live-state goldens are isolated per run and idempotent at start (RD-81)

What: `funded-pass-lock-golden.mjs`'s `cleanup()` selected a column named `id` on
`funded_pass_runlock`, whose primary key is `lock_key`, there is no `id` column. PostgREST returned
error `42703` on every call and `cleanup()` destructured only `{ data }`, dropping `error` (the
error-swallow anti-pattern CLAUDE.md's agent/run post-mortem names), so `ids` was always `[]` and
`guardedDelete` never ran. Every invocation, not only an OS-killed one, left its fixture holder (pid
990001) live in the production table forever; the next run's first acquisition correctly took over that
stale holder and failed the golden's own first assertion (expected `takeover=false`, got `takeover=true`).
Confirmed by reading the live row before touching code (`lock_key=funded-pass-golden-test`,
`holder_pid=990001`, `heartbeat_at=2026-09-22T17:29:16Z`, ~11 minutes stale) and reproducing the `42703`
error directly against the table. A second, independent defect: the golden's one FIXED test key meant two
gates running it concurrently on this PC raced the same row.

Fixed:

1. Per-run `lock_key` under a shared fixture prefix (`funded-pass-golden-test-<random>`), so concurrent
   runs cannot collide with each other or with the live `funded-pass` production key. Chose this over the
   pause-flag proof's rolled-back-transaction pattern because the golden calls `acquireRunLock`/
   `heartbeatRunLock`/`releaseRunLock` (the same functions production's `funded-pass.mjs` calls) over
   `supabase-js`'s `sb.rpc()`, i.e. PostgREST, a stateless HTTP transport where every `.rpc()` call
   auto-commits as its own transaction. There is no supported way to hold one `BEGIN` open across those
   separate requests through that client without bypassing the exact integration path the golden exists
   to prove.
2. `sweepStaleFixtures()` age-gates the idempotent-start sweep to fixture-prefix rows whose heartbeat is
   older than 30s (the golden's own scenario runs in low single-digit seconds), so a killed prior run's
   leftover is cleared without ever deleting a concurrently-running sibling's fresh row.
3. End-of-run cleanup deletes only the run's own key, for the identical reason.
4. `FUNDED_PASS_GOLDEN_PLANT_STALE=1` plants a stale fixture row via the golden's own `guardedInsert`
   helper (never hand SQL) and asserts the start sweep clears it.
5. RD-81 (`invariants.d/RD-81.mjs`) + remediation-discipline category 50 (new section in
   `.claude/skills/remediation-discipline/SKILL.md`). Enforcer: the golden's own concurrent self-test,
   already execution-wired via `run-goldens.mjs`.

Corrections made during the work: the first version of the fix swept the WHOLE fixture prefix
unconditionally at both start and end. This lane's own two-concurrent-runs attack caught it failing: one
instance's post-sweep re-check saw a row the OTHER instance had just inserted, a genuine cross-run
interference bug the fix itself introduced. Corrected to the age-gated sweep plus own-key-only end
cleanup described above, before landing. Several comment lines used em dashes, caught by rule 022 on the
first commit attempt and fixed.

Audited the other 15 goldens `run-goldens.mjs` runs for the same live-write shape (grep for
`.insert(/.update(/.delete(/.upsert(` plus a `jiti.import(".../db.mjs")` scan): only
`mutation-lease.golden.mjs` also writes a live shared table. Verdict: owed, not fixed here, different
shape (it already sweeps its own fixture id at start, unlike funded-pass-lock's actually-broken cleanup,
but shares one FIXED sentinel item id across every run, so it is not yet safe under two concurrent
gates). Every other golden does no live-table write.
