# 2026-10-08, lane SEC-1 (sec1-profiles-escalation): a user cannot change their own platform-admin flag (migration 364)

## Finding

- [CONFIRMED by catalog read, 2026-10-08, coordinator] role `authenticated` held UPDATE on `public.profiles` at table level (every column, including `is_platform_admin`). The only UPDATE policy, `profiles_self_update` (migration 165), gates rows (`auth.uid() = id`), not columns, and no trigger guarded the column. Any signed-in user could set `is_platform_admin = true` on their own row through PostgREST. Same exposure for `role`, `org_id`, `workspace_role`.
- [CONFIRMED by code read, this lane] the INSERT path had the same hole: `profiles_self_insert` (165) plus table-level INSERT let a user with no profile row create their own row carrying `is_platform_admin = true` before `ensureProfile` (service role) ran. Closed in the same migration (rule 13).

## Accomplished

- `fsi-app/supabase/migrations/364_profiles_privilege_columns.sql` (header NOT APPLIED; the coordinator's executor applies it before merge). Layer 1: `REVOKE INSERT, UPDATE ON TABLE public.profiles FROM PUBLIC, anon, authenticated` (table level, because a column revoke under a table grant is a no-op), then `GRANT INSERT (...)` and `GRANT UPDATE (...)` to `authenticated` on every live column (read from `pg_attribute`) except `is_platform_admin`, `role`, `org_id`, `workspace_role`. All four exist: `role` (001), `is_platform_admin` (075), `org_id` and `workspace_role` (105). Layer 2: `profiles_privilege_guard()` as a `BEFORE INSERT OR UPDATE` row trigger, SECURITY INVOKER, raising 42501 unless `current_user` is `service_role`, `postgres`, `supabase_admin` or the table owner.
- Self-check in the migration transaction, rolled back by a sentinel exception: as role `authenticated` with a fixture jwt sub, UPDATE of each of the four columns is refused by column privilege (message must say "permission denied", not the trigger); `UPDATE job_title` on the own row succeeds with 1 row; INSERT of an own row with `is_platform_admin = true` is refused, a plain own-row INSERT succeeds; then the four column grants are restored inside the rolled-back block and the same attacks must be refused by the trigger (message must name `profiles_privilege_guard`), so each layer is proven alone; as `service_role` the flag UPDATE succeeds. After the block, `has_column_privilege` is asserted for authenticated, anon and service_role.
- `364_profiles_privilege_columns.test.mjs` (15 tests, node builtins only). Red first: with the SQL file absent the file failed with ENOENT; with it present `node --test` shows 15 pass, 0 fail.
- `docs/inventories/migrations.md` regenerated with `scripts/inventories/generate-migrations-inventory.mjs --write` (325 rows, one added).

## Decisions

1. Table-level revoke plus column-level re-grant, not `REVOKE (col)`: the design's "revoke the four columns" is a no-op in Postgres while a table-level UPDATE grant exists, so the migration revokes at table level and re-grants the live columns minus the four. Consequence recorded in the header: a column added later has no authenticated INSERT/UPDATE grant until its own migration grants it (fails closed, 42501).
2. The guard keys on `current_user`, not on migration 201's transaction-local marker and not on a JWT claim. 201's marker exists because its sanctioned writer is an RPC even for service_role. Here the sanctioned writers are roles, and a SECURITY DEFINER function runs as its owner. [CONFIRMED by reading the definitions] `create_org_for_self` and `accept_invitation` do not write `profiles`, so no marker and no RPC change is needed; the brief's "STOP if a set_config is needed" did not trigger.
3. Extension beyond the written design (flagged in the PR): the INSERT path is covered by the same revoke, column grant and trigger, for the reason under Finding. `anon` is revoked and not re-granted (no policy ever let anon write profiles).
4. Consumers [CONFIRMED by grep, enforced by the new test]: user-session writes to `profiles` in `src` are `UserProfilePage.tsx persist()` (full_name, bio, avatar_url, jurisdiction_overrides, transport_mode_overrides, verifier_status = 'pending', updated_at), `OnboardingWizard.tsx` (transport_mode_overrides, jurisdiction_overrides), `NoWorkspaceLanding.tsx` (job_title), `lib/orgs/create-org.mjs` (job_title, region), `api/auth/linkedin/callback/route.ts` (linkedin_verified, verification_tier, full_name, headline, linkedin_url). None touches the four columns. `ensureProfile` inserts `role: 'member'` with the service-role client, which stays sanctioned.
5. Re-proof: PROOF-4 attack `admin-gate-self-promotion-refused` in `scripts/proof/attacks/attacks.json` (PR 985) re-proves the fix against the chain stack once 364 is applied there.

## Correction (first apply failed, coordinator report 2026-10-08)

- [CONFIRMED by the apply error] Migration 364 aborted and rolled back on its first apply: `23503 insert or update on table "profiles" violates foreign key constraint "profiles_id_auth_users_fkey"` at the self-check fixture `INSERT INTO public.profiles (id) VALUES (v_uid)`. Cause: `profiles.id` has a foreign key to `auth.users` that no migration file in the repo declares (the repo files showed `profiles.id` with only a default); this lane invented fixture ids and did not know the live constraint. Nothing was applied.
- Fix (coordinator design): the self-check no longer invents ids. UPDATE legs (A, B, D, E) use the oldest real profile (`SELECT id ... ORDER BY created_at LIMIT 1`), every change rolled back, skipped with a NOTICE if `profiles` is empty. INSERT legs (C, D2) use an `auth.users` row with no profile, else a fixture `auth.users` row inserted with only its id (assumption stated in a NOTICE: auth.users needs nothing else; if that insert fails the INSERT legs are skipped with a NOTICE and the privilege-catalog assertions still run). Attack values are computed to differ from the row's current value (`NOT is_platform_admin`, CASE expressions) so the trigger's `IS DISTINCT FROM` fires whatever a real row holds; the service_role leg asserts the value changed.
- Static test gained a test pinning that no fixture id is minted outside the single `gen_random_uuid()` that is inserted into `auth.users` in the next statement, and that every profiles INSERT in the self-check uses that id. Against the first SQL the updated test file fails 3 of 16; against the fixed SQL it passes 16 of 16.
- [HYPOTHESIS] unchanged risk: a live auth.users NOT NULL column without a default would make the fixture auth.users insert fail; that skips the INSERT legs with a NOTICE rather than aborting.
