## What was built

- `fsi-app/scripts/producers/market/sbti-target-dashboard-producer.mjs` (new). Fetches
  `https://files.sciencebasedtargets.org/production/files/targets-excel.xlsx` (confirmed live, the

  `market_series` rows:
  - `sbti:near-term-lead-time-<sector>` / `sbti:net-zero-lead-time-<sector>`, mean(target_year -

## Which workflow shape, and why

A new step inside `.github/workflows/producers.yml`, not a standalone file matching
`research-assessment.yml`'s shape. Reasons: (1) the brief's own text frames the choice as "matching
`producers.yml`'s existing per-producer step convention" vs. a standalone file, and every OTHER
`market_series` producer (`ecb-fx`, `eia-v2-petroleum-spot`, `eu-weekly-oil-bulletin`) already lives as
a step in this same file, a fourth market producer as a standalone file would be the inconsistent
choice, not the consistent one; (2) `producers.yml`'s trailer (Population AFTER, the harness-landing
pair, the cache-flush) already runs unconditionally for every dispatch of this workflow, so a new step
here gets harness-run landing "for free," with zero new wiring, matching rule 17 (nothing runs alone)
at no extra cost; (3) `research-assessment.yml`'s own standalone shape exists because research
assessment is a DIFFERENT family (`research-assessment`, not `producers`) with its own harness-run
artifact path, SBTi is squarely a `market_series` producer, the `producers` family's own domain.

## market_series contract for lane L10's LeadTimeChart.tsx, UPDATED after merging L10's own landed work

L10 merged to `origin/master` (#904, `6d34a596`) WHILE this lane was still building, in parallel, from
the same brief round. This lane merged `origin/master` into its own branch (see "Merge" in Gates below)
and found a REAL contract mismatch the merge itself surfaced, [CONFIRMED] by reading L10's actual
shipped code, not by guessing a shared contract in advance:

- L10's `src/lib/market/lead-time-position.mjs` `monthsValue()` gates on `row.unit === "months"` EXACTLY
  and never coerces a different unit (spec 02 section 6 item 5's own "months axis"). This producer was
  originally emitting `unit: "years"`. **Fixed in this lane's final commit** (95472ea2): both lead-time
  series now carry `value_numeric` in months (`leadYears * 12`, a real unit conversion the base/target-
  year source data supports exactly, never a fabricated finer precision) and `unit: "months"`.
  `sbti:commitment-removed-*` is unaffected (`unit: "companies"`, correctly excluded by L10's own unit
  gate either way).
- Verified end-to-end, live: this lane's `aggregateSbtiTargetRows()` output was fed directly into L10's
  `buildLeadTimePosition()` in a throwaway script (not committed, numbers reproduced here): a 5-row
  fixture produced ONE `sbti:near-term-lead-time-freight` series row, correctly picked up by L10's own
  `isSbtiSeriesKey` + unit filters, `cohortMedianMonths` computation path reached. (It correctly reports
  "not forecastable, 1 usable row, below the 5-row floor" for that tiny fixture, see the next point for
  why that is the right, non-bug behaviour.)
- **Two DIFFERENT sample-size concepts, both correct, not a conflict**: this producer's `n_observations`
  is the count of COMPANIES feeding one sector's averaged lead-time figure (a statistical floor WITHIN
  one row); L10's own `minSample` (default 5, `DEFAULT_MIN_SAMPLE`) counts the number of market_series
  ROWS (sectors) that clear the `unit === "months"` filter, a DIFFERENT floor across rows. Both are
  legitimate, named, documented gates at different levels, flagged here so neither lane mistakes the
  other's number for its own.
- Read series under key prefix `sbti:near-term-lead-time-*` and `sbti:net-zero-lead-time-*` for the
  chart's own lead-time figure; `sbti:commitment-removed-*` for survivorship is NOT currently read by
  L10's own shipped code (confirmed: `isSbtiSeriesKey` matches any `sbti:*` prefix, but `monthsValue`'s
  unit gate excludes the `"companies"`-unit removed-count rows from the sample either way); L10's own
  call whether survivorship ever becomes a second chart element.
- **Today this producer writes ZERO rows to the live database** (the licence gate, unchanged by the
  merge). L10/the supabase-server `fetchSbtiLeadTimeSeries` reader should render their own "not
  forecastable"/empty state for this reason alone until the licence resolves; confirmed this is already
  exactly what both sides do (L10's `reason: "no SBTi-sourced lead-time rows observed yet"` at
  `sampleSize === 0`), not a bug in either lane.
