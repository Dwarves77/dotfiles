- **Applicability gate** (`src/lib/applicability/compute-applicability.mjs`, new): pure,
  deps-injected function `computeApplicability(obligation, profile)` returning
  `{ status: 'applies' | 'does_not_apply' | 'needs_profile_input', reasons, missingDimensions }`.
  Multi-role orgs match on ANY held role in an obligation's `roleScope`; a size threshold compares
  band rank, not a number; missing dimensions are collected across BOTH gates (role and size) before
  reporting `needs_profile_input`, naming every missing dimension (absence-wording rule,
  2026-09-25 close). 11 unit tests covering multi-role orgs, a missing size dimension, both
  dimensions missing at once, and the `at_least`/`below` threshold edges (band exactly equal to the
  threshold; one band under it).

## UX compliance

- **Screen/block**: Organisation profile card, `/settings#general`.
- **Primary goal**: tell the platform which roles the org holds and its size bands, so
  role/size-scoped obligations can resolve applies / does not apply / needs profile input.
- **Path**: land on Settings (already the workspace-wide settings surface) → click role chips that
  apply → click one band chip per size dimension → Save. 2-3 clicks, no navigation.
- **One primary action**: "Save organisation profile" button, disabled until dirty; role/size chips
  are the input controls, not competing actions (law 7).
- **Feedback per async action**: Save shows "Saving…" then "Saved to {workspace}." inline (law 6);
  a failed save shows the Supabase error text inline, not silently (law 15); loading state ("Loading…")
  and no-workspace state are both named, never a blank card (law 10/20, no empty/ambiguous end
  state).
- **Targets**: chips reuse the existing `Chip` primitive (44px-floor-compliant per its existing
  usage elsewhere); Save button is 44px min-height.
- **Familiar pattern**: reused `AccountCard`/`Chip`/`FieldLabel` from `AccountPrimitives` and the
  exact read-modify-write/dirty-tracking shape `BriefingScheduleSection` already established, no
  new interaction pattern introduced (law 3, 16).

## Open questions / follow-ups

- `FreightSectorsCard`'s `setSectorProfile` toggle appears to be LOCAL zustand state only, no
  Supabase write is wired to it directly (the only write path found is `OnboardingWizard`'s
  `persistSectors`, run once during onboarding). This predates this lane and is outside its write
  set; flagged, not fixed here (out of scope: `SettingsPage.tsx`'s `FreightSectorsCard` function is
  in the same file as the addition but the pre-existing gap is a separate defect, not part of this
  workstream's profile/applicability build).
- Size-threshold applicability is wired but structurally unreachable from LIVE data today: no
  producer writes `item.size_threshold` (no schema field exists for it, per the ruling's "no new
  schema" constraint). The wiring is real and tested (`relevance.test.mjs`'s size-threshold test
  proves the plumbing), but a size-scoped obligation will only ever surface `needs_profile_input`
  or a real threshold comparison once a future, separately-ruled migration adds a size-threshold
  column somewhere (obligations or intelligence_items) and a producer starts populating it.
- `COMPLIANCE_OBJECT_TO_ORG_ROLE` maps 13 of 18 `compliance_object_tags` values; 5
  (`manufacturer-producer`, `distributor`, `port-operator`, `airport-operator`,
  `terminal-operator`) have no ORG_ROLES counterpart and are left unmapped (an item tagged only with
  one of these derives an empty roleScope, which reads as "applies to every role", not a false
  `does_not_apply`). Extending ORG_ROLES to cover infrastructure/manufacturing roles, if ever
  wanted, is a product/ADR question, not this lane's call.
