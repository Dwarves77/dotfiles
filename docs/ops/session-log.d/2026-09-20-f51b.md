### What landed

F51 check 5 (`fsi-app/.discipline/fitness/functions/F51-no-shared-append.mjs`, `runCheck5`) failed twice
by reading only `origin/master`'s trailing 30 first-parent commits and refusing whatever file crossed the
3-touch threshold, after the fact: `docs/dispatches/lane-briefs/2026-09-19/README.md` on 2026-09-19, then
`fsi-app/scripts/lib/loop-run-id.mjs`, `fsi-app/scripts/lib/loop-run-id.test.mjs` and
`fsi-app/scripts/turns/emit-downstream-chain-artifact.mjs` on 2026-09-20 (lane T3's push gate, step 3d
[CONFIRMED, brief evidence]), touched serially by lanes M3 (#752), M3b (#755) and M4 (#759). The gate could
never refuse the PR that made the third touch (at that PR's own gate, master still showed two), and once
that PR merged it refused every unrelated lane, including its own second occurrence blocking all other
lanes' pushes.

The fix:

1. `runCheck5` now resolves the lane's own changed-file range the same way checks 1-4 already do (reuse of
   `resolveRange` + `gitChangedFiles` from `change-range.mjs`, no second derivation). A hotspot is a
   VIOLATION only when the current range touches the file: count = touches on `origin/master` in the
   30-commit window (after the dated anchor) plus one for this range, threshold 3 unchanged. The message
   names the prior commits (sha, subject) that already touched the file.
2. A hotspot the current range does not touch is still printed as the standing number, exactly as before,
   and is never a violation (the bystander case -- this is lane T3's exact situation, used as the fixture).
3. On `origin/master` itself, or any run with an empty or unresolvable range (a push to master, a
   scheduled or manual run), the check prints the standing number and returns no violations.
4. New pure core `evaluateHotspotViolations` (unit-tested per brief item 3(a)-(e): RED two-prior-touches
   plus range touches; GREEN three-prior-touches with range not touching, bystander; GREEN empty range;
   RED-still allowlisted-vs-non-allowlisted in the same range; message names prior commits). Git-fixture
   end-to-end tests exercise the same semantics through `runCheck5`'s own range resolution (lane branch
   checked out from a fixture `origin/master`, matching the checks 1-4 fixture pattern).
5. `parseFirstParentLog` unchanged (still tested, still exported); a new `parseFirstParentLogDetailed`
   parses `sha` + `subject` + `files` per commit (a shared `splitLogBlocks` helper avoids duplicating the
   `%x01` block-split between the two parsers).
6. Three dated `HOTSPOT_ALLOWLIST` entries added for the loop-id-resolver files (coordinator-decided text,
   verbatim from the brief), and the pinned-keys test (`HOTSPOT_ALLOWLIST names only ...`) updated to the
   new ten-entry set.
7. Header comments on check 5 and the `fitnessFunction.description` corrected to the present design,
   dated history kept.
8. Runbook: no existing F51 paragraph was found (`grep -rni "F51\|no-shared-append\|hotspot" docs/runbooks/*.md`
   returned nothing before this change) -- F51 was introduced 2026-09-19 by lane N6, which never wrote
   runbook documentation for it. This lane added a new Appendix entry to
   `docs/runbooks/MAINTENANCE-RUNBOOK.md`, matching that file's existing "Appendix: <gate>, wired via ..."
   convention for discipline-gate documentation (the closest prior art found; the file otherwise documents
   numbered data-maintenance runtimes, not fitness-function gates). `docs/runbooks/CORPUS-TURN-RUNBOOK.md`
   was considered and rejected: it already carries 2 touches in the current 30-commit hotspot window
   ([CONFIRMED], counted from `git log --first-parent -n 30 --name-only ccb6aa0c..origin/master`), and
   editing it would make this very lane's own range trip check 5's new gate (3rd touch). MAINTENANCE-RUNBOOK.md
   carries 0 touches in the same window, confirmed safe.
