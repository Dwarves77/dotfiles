## Built

- `fsi-app/scripts/verify/lib/ui-orphan-scan.mjs` + `.test.mjs` (18 tests), pure core, the FIELD-grain
  sibling of F14 (`.discipline/governance/producer-consumer-orphan.mjs`, which is table-grain). Parses
  PostgREST `.select("...")` strings into (table, column) pairs (bare columns, `alias:column`,
  `embed_table(nested...)` recursion); extracts writer columns from `.insert/.update/.upsert({...})` object
  literals, the guarded-write helpers (`guardedInsert`/`guardedInsertMany`/`guardedUpdate`/`insertFn`), SQL
  `INSERT INTO (...)`/`UPDATE ... SET`, and RPC calls joined to their own migration function body's writes
  (coarse, whole-body join, same granularity note F14 already carries for RPCs).
  - **False-positive correction, made same-session before reporting** (see Corrections): the first live run
    against 472 UI-facing files found 185 "orphan" fields, almost all fields written through a helper
    function's row-builder (e.g. `scripts/gen/emission-factors-common.mjs`'s `buildRow()`, called as
    `insertFn("emission_factors", toWrite, {...})` where `toWrite` is a variable, not an inline object
    literal this parser can trace). Added `extractOpaqueWriteTables()`: any write call whose payload is NOT
    a literal object (or `[{...}` array-of-objects) marks that WHOLE table's columns as
    write-uncertain and suppresses them from column-level findings, conservative by construction (trades a
    possible missed finding for eliminating the high-false-positive failure mode F14's own header already
    names as the reason field-level analysis stays informational there). Live count dropped 185 → 16 after
    this fix.
- `fsi-app/scripts/verify/ui-orphan-audit.mjs`, runner. `// data-audit: label=ui-orphan hard=false`. Scope:
  API routes (`src/app/**/route.ts`), pages (`src/app/**/page.tsx`), `src/components/**/*.tsx`, and
  `src/lib/supabase-server.ts` (CLAUDE.md's own Key Files entry for "the server-data layer feeding pages").
  Writer corpus is broader (all of `src/`, `scripts/`, migrations, `supabase/functions`), matching F14's own
  writer-scan scope. Reuses `information-schema-scan.mjs` (shared, TOOL-GAP-2) for the live schema and
  `dead-column-scan.mjs`'s `scopedColumns` (excl. PK/FK/generated/timestamp, same scoping reasoning: those
  columns are "used" by a join/default/clock, not a literal write-site identifier).
- `fsi-app/scripts/verify/ui-orphan-allowlist.json`, empty by design (see Live run, the one live finding
  candidate for allowlisting, `state_cost_facts`, is a RULED build item, not an allowlist candidate).
- `fsi-app/scripts/verify/lib/harness-family-walk-scan.mjs` + `.test.mjs` (8 tests), pure core, extending
  F50's (`fitness/functions/F50-loop-wiring.mjs`) "every hop fires" pattern past the 11 named loop hops to
  EVERY registered harness family. Reuses `family-registry.mjs`'s `loadFamilies()` (no second family-listing
  scan) and F50's own `<family>-run-NNN.json` naming convention for run artifacts. Summarizes each family's

**Ruling 2 (xargs exit-code flake, rule 13).** Coordinator asked for a decision-ready writeup: exact
repro, observed vs expected exit code, responsible file/line, and a fix (as a diff, if in-scope) or a
stop-at-decision-ready.

**Investigated further; the original "pre-existing flake, unrelated to this diff" claim above is
`[REFUTED]` and corrected in place per rule 14/rule 13's corollary.** It was NOT an infra flake. Root
cause: this lane's own `ui-orphan-audit.mjs` header added a new `GOVERNING SKILL: remediation-discipline`
citation with no matching `skill-acks/<date>-<lane>.md`, which is exactly what
`fsi-app/.discipline/skill-drift-gate.test.mjs:49` (real-repo proof, calling `checkDrift()` from
`skill-contract-map.mjs`) exists to catch, a real, deserved test failure, not a spurious one.

- **Repro**: `node fsi-app/.discipline/lib/test-discovery.mjs > /tmp/filelist.txt && node --test
  $(cat /tmp/filelist.txt)` (bare, no `xargs`, isolates the test-runner's own exit code from any pipe
  artifact).
- **Observed (before the skill-ack fix)**: `ℹ tests 7955 / ℹ pass 7949 / ℹ fail 1`, one real failure at
  `fsi-app/.discipline/skill-drift-gate.test.mjs:51` (`assert.equal(ok, true, ...)`, `false !== true`),
  process exit 1. Through `run-test-suite.sh`'s own `... | xargs -0 node --test` line, that becomes
  `xargs`'s exit 123 (its documented code for "invoked command exited 1-125"), which is what the
  `pre-push` hook's step 3 reported as `STEP 3 FAIL` and what blocked the first `git push` attempt.
- **Why the summary in one earlier ad hoc run looked like "0 fail" while the shell still exited
  non-zero**: that run's `tail -40`/`tail -60` window of a 9,700+ line log happened to land past the one
  failing test's own report block (which prints well before the file-level summary in `node --test`'s TAP
  output when many suites run concurrently), so the truncated view showed only the trailing, unrelated
  passing tests plus the FINAL summary line, which itself is accurate (checked with `grep -n "^ℹ fail"` on
  the full untruncated log afterward, confirms `fail 1` was present earlier in that same file, just outside
  the tail window read at the time). Not a Node/xargs bug, a self-inflicted truncated-log misread.
- **File/line responsible**: not `run-test-suite.sh` at all, the responsible file is this lane's own
  `fsi-app/scripts/verify/ui-orphan-audit.mjs` line 2 (the new citation) missing its ack.
- **Fix**: already applied and committed this session, `fsi-app/.discipline/governance/skill-acks/
  2026-09-25-tool-gap-3.md` (see Built, above). Before/after: `node --test $(cat filelist)` exit 1 (1
  fail) before the ack commit; exit 0 (0 fail, `checkDrift().ok === true`) after it, verified directly via
  `node -e "import('./.discipline/governance/skill-contract-map.mjs').then(m =>
  console.log(m.checkDrift()))"` returning `{ ok: true, problems: [] }`. The actual `git push` (through the
  real installed `pre-push` hook, not a manual invocation) then completed cleanly end to end: "all 4 checks
  pass; push proceeding."
- **No change needed in `run-test-suite.sh`** (it was already correctly propagating a real failure); no
  separate commit for it. `xargs`'s exit-123 wrapping of a 1-125 child exit code is standard, documented
  behaviour, not a bug to fix.
