# 2026-10-03, lane RW-WF: land research-walker.yml's harness-run row the way research-assessment.yml does

## Defect (as dispatched)

The first dry dispatch of `.github/workflows/research-walker.yml` (run 37096258352, PR 898) completed
with every step reporting SUCCESS, but `record-harness-run.mjs` printed "best-effort, no-ops cleanly
with no SUPABASE_* creds set" and no row landed in `harness_runs`. The sibling
`.github/workflows/research-assessment.yml` (PRs 887, 891, 895) lands its row correctly (run
37091503805 produced `research-assessment-run-001`).

## Root cause [CONFIRMED, read both workflow files in full]

`research-assessment.yml`'s `assess` job wires `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`
at JOB-LEVEL `env:` (lines 65-68 on origin/master), so every step in that job -- including its harness-
run landing step -- inherits the secrets. `research-walker.yml`'s `walk` job had NO job-level secrets
env at all; the only place those two secrets appeared was inside the "Chained dry-run guard" step's own
`env:` block, scoped to that one step. The landing step therefore always ran with
`NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` unset, `record-harness-run.mjs` correctly self-
skipped (exit 2, rule 15's "no-cred case"), and the landing step's own `|| echo "record-harness-run:
best-effort, no-ops cleanly with no SUPABASE_* creds set."` swallowed that exit code so the step read
SUCCESS. Rule 17 ("a runtime is not done until the harness has recorded the outcome in harness_runs")
was violated silently, and nothing caught it because exit 2 is explicitly non-fatal by design (rule 15).

## Correction to lane L7's addendum (`docs/ops/session-log.d/2026-10-02-l7.md`)

Per the dispatch (and rule 13's corollary: a flag that dissolves under evidence gets a correction, never
a silent drop -- here the correction runs the other way, into this lane's own file, since lane
contracts forbid editing another lane's session-log entry): L7's addendum does not literally say "zero
DB credential, by design" about the harness-landing step -- it says (lines 96, 106) "no DB credentials
exist in a lane WORKTREE," which is true and describes the EXECUTOR LANE's own development environment,
never the deployed GitHub Actions job's secret wiring. But `research-walker.yml`'s own header comment
(as merged) framed the landing step's missing-credential self-skip as an accepted "best-effort, same
posture as every other producer" outcome -- language that reads the wiring gap as an intentional
design choice rather than naming it as the defect it was. [CONFIRMED] it was not a design choice: it was
a missing job-level `env:` block, the same block research-assessment.yml already carried. There is no
live/apply path difference between the two workflows that would justify research-walker.yml's landing
step having fewer credentials than research-assessment.yml's -- both land into the same `harness_runs`
table through the same `record-harness-run.mjs`, and the landing step's own DB write needs service-role
creds regardless of whether the PRODUCER upstream of it ran dry or live.

## Fix

1. **`.github/workflows/research-walker.yml`** -- added the identical job-level `env:` secrets block
   research-assessment.yml's `assess` job already carries (`NEXT_PUBLIC_SUPABASE_URL`,
   `SUPABASE_SERVICE_ROLE_KEY`), with a comment naming the defect this closes. The walker itself is
   unchanged: `RESEARCH_WALKER_ENABLED` stays `'0'` in this job's env (fixture-only, dry), `ENABLED` in
   `research-walker.mjs` is untouched, and the `mode` input still offers only `dry` -- no live/apply path
   is armed by this lane, exactly as the dispatch required.
2. **Landing step, both the shell logic in `research-walker.yml`** -- replaced the `|| echo
   "best-effort..."` swallow with explicit exit-code handling (`set -o pipefail`; capture `$?`; exit 2 is
   logged as a self-skip and the step continues; any other non-zero exit prints `::error::` and the step
   itself fails) -- the same pattern `scripts/turns/deliver-artifact-branch.sh` already uses for the
   families it serves, never a second implementation of that pattern.
3. **`fsi-app/scripts/lib/record-harness-run.mjs`** (shared module -- every harness family's landing
   goes through this one file, so the fix closes the CLASS, not just this one instance, per
   `remediation-discipline`'s class-over-instance principle: signal 3, shared codepath, fires). Added a
   third, deps-injectable check: when `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are missing
   AND `isGitHubActions` is true (default: `process.env.GITHUB_ACTIONS === "true"`, which every real
   Actions runner sets and no local developer shell does), `runCli` now returns exit 1 (a real failure)
   instead of exit 2 (self-skip). A genuine local developer run with no creds is unaffected (still exit
   2, rule 15's original intent). This closes the hole even if a FUTURE workflow repeats the exact same
   job-level wiring mistake research-walker.yml made: the shared landing module itself will no longer let
   a no-cred run in CI pass as a clean no-op.
4. **`fsi-app/scripts/lib/record-harness-run.test.mjs`** -- forced `isGitHubActions: false` on the
   pre-existing local-self-skip test (it would otherwise flip under real CI, where `GITHUB_ACTIONS=true`
   is always set, breaking the test's own premise); added three new tests: the CI-fail-loud case (exit 1,
   explicit `isGitHubActions: true`), a check that the failure message never claims to be a self-skip,
   and a check that the real default reads `process.env.GITHUB_ACTIONS` (not hardcoded true/false), by
   setting and restoring that env var around the call.
