## 2026-10-07, lane proof3-chain-steps (PROOF-3): the chain's scripts run in apply mode on the proof stack, with a read-back after every step

Third lane of the chain proof (ADR-045, PR 975 open). Nothing here ran against a database or the network: every behaviour is proven on stubs and fixtures, and the lane was not fired. Facts below were run or read in this lane.

### Accomplished
- `fsi-app/scripts/proof/steps/` (new): `chain-steps.json` (the manifest), `manifest.mjs` (load and validate against the hop registry), `assertions.mjs` (read-back assertions), `verdict-fixture.mjs` (run-time ledger verdicts), `prepare.mjs` (two step preparations), `run-chain-steps.mjs` (the runner and CLI), `live-prompt-version.mjs` (reads the live prompt version through jiti), and five `*.test.mjs` files. 65 tests, all passing under `node --test`, and also under the discipline job's no-npm sandbox (`node --import ./.discipline/lib/no-npm-sandbox.mjs --test`). `glob-portability.test.mjs` passes (10 of 10).
- The manifest has 19 steps: a preconditions step, 17 script steps and a closing hop-order check. The script steps are the 13 hops of `.discipline/governance/loop-hops.d` (01 to 13, in order) plus the four roots that feed them (Source sweep, Data producers, Brief apply, Research walker). Each script step is the workflow's own run lines in bash, mode apply, with the environment the workflow_run event would have provided (the step's own `GITHUB_RUN_ID`, the upstream step's run id as `GITHUB_EVENT_WORKFLOW_RUN_ID`, `GITHUB_EVENT_NAME`). `manifest.test.mjs` checks the manifest against the real hop files: every hop covered by a step whose workflow file is the hop's consumer and whose upstream name is the hop's producer, hops in numeric order, every step with an assertion, every script passing `bash -n`.
- The runner: for each step it reads the database clock, runs the var queries, the prepare hook, the setup statements and the snapshots, takes the baselines, runs the script under bash, lands every NEW harness-run artifact into the local `harness_runs` with `scripts/lib/record-harness-run.mjs`, then evaluates the step's assertions plus three it adds (the family's row carries the step's run id; a chained step's row carries the upstream's run id; a loop step's row carries the sweep's loop run id). The first failure stops the run with the step, the assertion, the table, the predicate and the observed value. The last step re-reads the ledger and checks every step landed, in order, linked and carrying the loop id (`checkHopOrder`).
- Assertions named in the brief: Population turn (mint row; `intelligence_items` grew by the mint artifact's `minted` count, floor 1; every item created in the step has at least one claim; the flywheel outcomes are recorded), Corpus turn (`item_cross_references` grew), Downstream chain (`vocabulary_terms` > 0), Propagation drain (events drained, or the row records `events_considered = 0`), Source resolution (`sources_promoted` >= 1 in the harness row, and the provisional count fell), Brief apply (`full_brief` of the target items differs from the snapshot taken after the reset).
- The flywheel gate (rule 17): Population turn runs `run-population-flywheel.mjs --check-gate` first against an empty mint history directory (B3 of the design: the committed history makes the gate refuse permanently), and after the flywheel against a directory holding only this run's own mint artifact; the second call must exit 0.

### Decisions
- Hop 02 (Ledger consume) runs the dispatch path's flags (`--mode apply --limit 2000 --max-promote 50 --record-only true --verdicts <fixture>`) under the chained path's upstream environment. The chained path of `ledger-consume.yml` can only discover the committed verdict batches, all stale.
- Hop 07 (Propagation drain after Downstream chain) runs the dispatch inputs the F60 fallback passes (`--chained true`, upstream name and run id); the proof job holds no token, so `gh workflow run` is not called.
- Data producers runs `producer=ecb-fx` only: `producer=all` includes a producer that needs `EIA_API_KEY` (a name the preflight forbids) and producers on rate-limited public APIs.
- Brief export passes explicit ids (verified, record-grade, unarchived items, 5) instead of the inline selection script embedded in `brief-export.yml`, which would have to be copied.
- Brief apply: the committed batches name production items briefed long ago, so the prepare hook keeps the entries (at most 3) whose item the local database holds, in a copy of the file, and the manifest's setup statement resets those items to record grade with no brief (replication role) so the apply has something to write; the assertion is that `full_brief` differs from the snapshot taken after the reset.
- Population turn's growth assertion uses the mint artifact's `minted` count, not `valid`: `valid` includes payloads held for a reason such as `not_applied_url_holder`, which would make the assertion fail on correct behaviour.
