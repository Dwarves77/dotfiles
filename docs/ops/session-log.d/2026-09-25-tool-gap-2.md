## Corrections (recorded honestly)

1. First cut of the duplicate-table checker used a bare `fkTarget>=0.6` threshold with no minimum
   set-size guard, which flagged 208 pairs, the great majority were two single-FK "edge" tables that
   happen to point at the same one table (e.g. both FK to `intelligence_items`), which is the single most
   common shape in the schema, not structural similarity. Caught by eyeballing the live output before
   committing. Fix: added `MIN_FK_TARGETS_FOR_SIGNAL = 2` (both sides need at least 2 distinct FK targets
   for the FK-target signal to apply at all), re-tested (added a fixture test for exactly this case),
   re-ran live: 208 -> 57. The column-name signal was never affected.
2. First cut of `dead-column-audit.mjs` and `column-existence-parity.mjs` (pre-existing) both hand-rolled
   an identical `readdirSync`/`statSync` recursive walker. F45 (duplicate-code ratchet) caught the +22
   line regression on the first full test-suite run (5,933 vs base 5,911). Fix: extracted
   `fsi-app/scripts/lib/walk-files.mjs`, both callers now import it; re-measured: 5,911 (no regression).
3. An earlier local CLI invocation of `.discipline/governance/coverage-scan.mjs` (used to diagnose the
   F23 orphaned-proof finding below) wrote a large diff to the committed `coverage-report.json` as a
   side effect. Reverted with `git checkout --` before committing, not part of this lane's write set.
4. F23 (governed-surface-coverage) initially reported both new `.test.mjs` files as ORPHANED PROOFS.
   Root cause: `execution-wiring.mjs`'s `testSuiteMatcher()` resolves via `git ls-files` (tracked files
   only), and the two files were untracked at that point. `git add`ing them (already required before any
   commit) resolved it, not a defect in either file, just staging order.
