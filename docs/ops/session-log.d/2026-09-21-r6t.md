## 2026-09-21, lane R6t: the family registry test derives from the directory, no pinned list

What: `fsi-app/scripts/harness-runs/family-registry.test.mjs` pinned a hand-kept `LIVE_FAMILIES` array
that every new harness family lane had to edit at the same line (the exact collision shape build plan
section 6.8 removed from the registry itself: two family lanes in flight always collide there, as
recorded 2026-09-20 by the M9d/M4 rebase conflict adding "producers" and "brief-export" to the same
line). I deleted the pinned list and replaced its one test with assertions derived from the tree:

1. `(a)` `FAMILIES` (loaded from `family-registry.mjs`) equals exactly the set of directories under
   `fsi-app/scripts/harness-runs/` that contain a `family.json`, compared against a fresh `readdirSync`
   of the live tree, not a literal.
2. `(b)` every loaded descriptor's `governing_files` is a non-empty array of strings (kept from the prior
   test; the family-equals-directory-name and other shape checks are already enforced inside
   `loadFamilies`/`validateFamilyDescriptor`, so a mismatched descriptor would have thrown before `FAMILIES`
   could exist at all).
3. `(c)` PROTECTION: a new helper `unregisteredFamilyDirectories()` (test-local; no natural home in
   `family-registry.mjs`, which is about descriptors, not run-artifact filenames) scans every directory
   under harness-runs and flags any that hold a committed `<family>-run-NNN.json` artifact
   (`isRunArtifactFilename` from `scripts/lib/run-artifact.mjs`) or a `pending/` folder but have no
   `family.json`. Asserted empty against the live tree. This is the protection the old pinned list gave
   by accident (a missing entry would fail the exact-set check) restated as a direct fact about the
   directory's contents.
4. `(d)` attack fixtures (rule 15, proven by attack not presence), all on `mkdtempSync` fixture trees:
   a directory with a committed run artifact and no descriptor fails `(c)`; a directory with a `pending/`
   folder and no descriptor fails `(c)`; a descriptor whose `family` differs from its directory already
   fails `(b)` via the pre-existing `loadFamilies` throw test (no new duplicate test added); a new valid
   family directory added to a fixture tree passes with zero edits to this test file.
