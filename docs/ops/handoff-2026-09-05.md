## 2. What Caro's Ledge is, and what "the build" is

Caro's Ledge (Freight Sustainability Intelligence) is a Next.js + Supabase product that turns
regulatory and market source material into structured, cited intelligence for freight/logistics
customers, surfaced across five customer surfaces (Regulations, Operations, Market, Research,
Community) plus an operator admin layer. **[CONFIRMED, `docs/plans/complete-system-build-plan-2026-09-04.md`,
read in full]**

**The loop (plan §1), in prose**: sources are discovered (`SOURCES` table) and swept
(`source-sweep`) for candidate links; candidates become `portal_link_candidates`, consumed
(`ledger-consume`) into either a specific document to census or a portal to keep sweeping;
accepted documents enter `census_worklist`; THE GATE mints qualifying census rows into
`intelligence_items` (this is the one chokepoint where a document becomes a live intelligence
item); minted items are enriched — connections (the flywheel's discovery half), forward events
(obligation dates/deadlines), obligations, tags/signals/classifications, the last with **no
human gate** (ADR-025) — and enrichment results propagate through an outbox/DAG/drain mechanism
to notices, which customer surfaces read; producers (market-data/statutory computation modules)
feed the same propagation graph; and a separate heal/grounding mechanism (Gate A, the STEP
SOURCE registration/rating step, and source tiers) keeps every published figure traceable to a
rated source. This is **two mechanisms**, not one, per the ledger skill's standing correction:
connection discovery is live pure computation with no LLM; decision propagation (the DAG/outbox)
is the newer, still-completing half.

**The six-part definition of done (plan §0)**, applied to every component before it counts as
built: (1) **Reachable** — a real caller exists (a route, a workflow_run: line, a chokepoint
import), proven by F25/execution-wiring green, not by the file merely existing; (2) **Run** — at
least one real execution left a harness-run artifact or a guarded write with a read-back;
(3) **Populated** — the table/column has live rows, proven by read-only SQL, not by "the
migration is written"; (4) **Visible** — a customer or operator surface renders it, checked by
the rendering guard and (for a new surface) a screenshot; (5) **Gated** — a fitness function,
contract test, or golden fails CI on regression; (6) **Documented** — a runbook section,
inventory row, and (when a governing file changed) a re-pinned F28 marker. Anything that cannot
clear all six is deleted with its test and inventory row in the same lane, never left
half-built — this is rule 13 ("a flag is a commitment, not a comment") applied to the DoD
itself.

## 3. How work is done

**Roles** (operator ruling, restated "many many many times" per the dump, and codified nowhere
as a numbered CLAUDE.md rule because it is procedural, not a product invariant — **[operator
ruling, chat]** for the framing, cross-checked against CLAUDE.md's actual content which does not
contradict it): the operator rules; the coordinator (this Cowork/Claude session, and its
successor) coordinates only — it writes lane briefs from the build plan, launches Sonnet/Haiku
lanes via the Workflow tool, lands their work through the browser transport (§4), applies
migrations via the Supabase MCP, dispatches GitHub Actions workflows through the "Run workflow"
popover, records the dispatch ledger, and reports; it does not write code, tests, or docs
content itself, and does not fix gates itself. Sonnet lanes build (code, schema, tests,
migrations); Haiku lanes do bulk text work — proposer passes, classification verdicts, ruling
drafts, browser worklists. Neither Opus nor a "Fable"-class model is used for lane work; the
operator's words, quoted in the dump: "stop offering API when you have a free option with
Haiku."

**The lane lifecycle**: a lane is briefed from the build plan (a `.js` file under
`docs/dispatches/lane-briefs/<date>/`, see that folder's own README for the format) → given a
fresh worktree under `/root/work/lanes/<name>` on a branch off a named `origin/master` (or
train) commit, with `fsi-app/node_modules` symlinked so it need not install its own → the lane
reads its brief's citations in full, builds, tests, and commits inside its own write set → the
coordinator lands the lane's commits via the browser transport (a lane cannot push) → once
landed, a proposer pass (a Haiku lane, per F28 rule (d)) attests the harness-run artifacts the
new code produced → a row is appended to `docs/ops/dispatch-ledger.jsonl` → the board and
session-log are updated in the same train. Multiple lanes run concurrently in disjoint
worktrees with disjoint write sets, named explicitly in each brief so two lanes never edit the
same file; a lane that needed a path outside its write set says so in its report rather than
reaching for it.

**The Workflow-tool mechanics** (see the lane-briefs README for the full format spec): a brief
file exports `meta` (name/description/phases), calls `phase('Title')` to open a phase, and
calls `agent(promptString, { label, phase, model })` once per lane dispatched, ending with a
`return` of all lanes' results. **At most two agents run concurrently per Workflow-tool
invocation** — a measured constraint, not a policy: postscript 23 states "the Workflow tool
caps concurrent agents per workflow at this container's CPU count (2)." A wave needing more
than two lanes splits across more than one brief file or more than one dispatch.

## 4. The browser transport, step by step

The container cannot push to `origin` directly (git proxy returns 403). Every landing goes
through the browser. This section is transcribed from the dump's own §6 and has **not** been
independently re-run by this lane this session (no Chrome/Codespace access from a docs-only
lane) — treat every step as `[operator-established procedure, dump §6]` unless marked
otherwise, and re-verify the click coordinates against the live page before trusting them (a UI
redesign or a different viewport will move them).

1. **Bundle.** In the lane's own worktree: `git bundle create /mnt/user-data/outputs/<name>.bundle
   origin/master..HEAD`.
2. **Upload.** Open a Chrome tab on `https://github.com/Dwarves77/dotfiles/upload/master`, use
   `find` to locate the file input, then `file_upload` with the bundle's path. Click "Propose
   changes" (reported screen position `(361,657)` — a coordinate, not a stable API; find the
   button by text/role first, fall back to the coordinate only if `find` fails), wait 3 seconds,
   and click again (GitHub's upload flow needs two submits under load). This creates a branch
   named `Dwarves77-patch-1` holding the raw bundle file as a diff.
3. **Codespace "turbo invention"** (the Chrome tab is titled `Welcome - dotfiles [Codespaces:
   turbo invention]`). Click inside the terminal pane before typing anything — **the first
   keystroke after any idle period is commonly lost**, so retype the first character/word if
   the terminal shows a truncated command. If the codespace has stopped, click "Restart
   codespace" (reported position `(719,272)`) and wait ~80 seconds for it to come back.
4. **Landing command** (one line, run in the Codespace terminal once it is live):
   ```
   clear; git fetch origin master Dwarves77-patch-1 && git show origin/Dwarves77-patch-1:<name>.bundle > /tmp/x.bundle && git fetch /tmp/x.bundle HEAD:refs/heads/<branch> && git push -u origin <branch> && gh pr create --fill --head <branch> && sleep 120 && gh pr checks <branch> --watch --fail-fast && gh pr merge <branch> --squash --delete-branch; git push origin --delete Dwarves77-patch-1; git checkout -q master && git pull --ff-only && git log --oneline -1
   ```
   This fetches the uploaded bundle back out of the throwaway `Dwarves77-patch-1` branch,
   replays it onto a real branch name, pushes, opens a PR, waits for CI, merges (squash,
   deleting the branch), cleans up the throwaway branch, and lands back on an up-to-date
   `master`. The final `git log --oneline -1` is the landing proof to paste into the dispatch
   ledger or the session-log entry.
5. **Fast-forward variant**, for an existing PR branch rather than a brand-new one: replace the
   `gh pr create …` clause with `gh pr checks <PR#> --watch --fail-fast && gh pr merge <PR#>
   --squash --delete-branch`.
6. **Reading CI logs**, in the same Codespace terminal: `gh run view <run-id> --log-failed >
   /tmp/l.txt; grep -nE '✖|EXPIRED|##\[error\]' /tmp/l.txt`.
7. **Dispatching a workflow via the "Run workflow" popover**: navigate to
   `https://github.com/Dwarves77/dotfiles/actions/workflows/<file>.yml`, wait ~10 seconds for
   the page to settle, click "Run workflow" (reported position `(1183,219)`), wait ~9 seconds
   for the popover's inputs to render, `find` each input field and fill it with `form_input`,
   then click the green submit button. The dump notes this "usually needs 2-5 click cycles" —
   i.e. do not assume the first click landed; re-`find` and confirm the popover state before
   re-clicking. After a successful dispatch, record a row in
   `docs/ops/dispatch-ledger.jsonl` (schema below, §5) in the same train.
8. **Known failure modes**: the first typed keystroke after the terminal has been idle is often
   dropped (retype); a stopped codespace needs the restart click and an ~80 s wait; a frozen
   renderer can make a screenshot/read-page action time out — wait 5 seconds and retry once
   before concluding the page is actually broken. A background Chrome tab throttles timers and
   never fires `IntersectionObserver`, so never measure live-site performance (scroll behavior,
   lazy-load timing) from a hidden/background tab — use Resource Timing or `x-vercel-cache`
   response headers instead, read from a foregrounded tab.

## 8. Errors and lessons

From the dump's §11, each restated as "what happened → the rule now":

- **Re-granting F25/F38 expiries (41 → 43 → 46) instead of closing W7.1** → master went red the
  instant train 46 landed. **Rule now**: an allowlist entry is granted once, with a named lane
  and a real reason; it is never re-granted a second time. W7.1-CLOSE's brief states this in
  capital letters as FORBIDDEN.
- **Diverging from the plan into perf work and source sweeps** (sweep dispatches #16-#22,
  #22 itself cancelled mid-flight) → an explicit operator stop: "you diverged from the plan."
  **Rule now**: no further source-sweep dispatches until the plan itself is built out (§7's
  worklist has none); a coordinator that finds itself doing unplanned work stops and asks,
  rather than continuing because the unplanned work is also useful.
- **The coordinator doing lane work itself instead of dispatching Sonnet/Haiku** → an operator
  correction, restated as the roles rule (§3). **Rule now**: the coordinator briefs and lands;
  it does not write code or docs content.
- **ledger-verdicts-001: 308 of 338 candidates rated from wall shells, not real content** →
  pruned down to 30 genuinely-rated verdicts. **Rule now**: rule 18 (get the source, then rate
  it) applies to classification inputs too — a bot-wall shell is not a source, and rating one
  is the same defect as citing an unfetched figure.
- **Hidden-tab performance measurements** — `IntersectionObserver` never fires in a background
  tab, so early perf numbers were wrong until corrected. **Rule now**: measure the live site
  with Resource Timing / `x-vercel-cache` headers, or from a foregrounded tab; never trust a
  background tab's scroll/visibility behavior (§4's failure-modes list).
- **Sweep dispatches #16/#17 killed at the 30-minute job timeout with no artifact at all** →
  built lane SWEEP-BUDGET (20 s per-fetch timeout, 1,500 s wall-clock budget, writes a partial
  artifact on exhaustion instead of nothing). **Rule now**: any long-running dispatch needs a
  budget that guarantees a partial artifact, never an all-or-nothing timeout.
- **Disk full from ~40 landed worktrees accumulating** → worktrees for already-landed lanes
  were removed; only `perf12merge` was kept (as a base for a later merge lane). **Rule now**:
  remove a lane's worktree once its work has landed; do not let them accumulate.
- **A PR failed C3 because an inventory row named a migration draft that had since been
  deleted/renumbered** → **rule now**: an inventory row is only ever written to name a migration
  file that actually exists at that path; the moment a migration is renumbered or removed, its
  inventory row updates in the same commit (this is also why §6's migration table above states
  plainly that 308-311's inventory rows must flip to "applied" the instant they are, in the very
  next train — not left stale).
- **A no-npm CI job failed because a test imported a module that transitively imports
  `@supabase/supabase-js`** (absent in that job by design) → fixed with a dependency-free
  env-predicate module. **Rule now**: any code a no-npm test suite imports must be checked for
  its full transitive import graph, not just its own direct imports, before assuming it is
  npm-free.
