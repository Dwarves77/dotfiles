A sub-select inside a policy runs as the querying role, so the parent table's RLS applies to it: for anon and authenticated the sub-select can only find parents that `intelligence_items_read` lets them see, i.e. verified and not archived. A child row of a quarantined (not verified) parent is therefore NOT readable by anon or authenticated through these four policies; the `is_archived = false` clause adds nothing the parent policy does not already require. Verdict for these four: no exposure; POL-3 stands only as a policy-shape inconsistency (the siblings item_changelog, item_timelines, etc. repeat `provenance_status='verified'` explicitly, these do not). Corroboration, not the basis: AT1 2026-10-08 section 10 counted anon reading 6,143 of 12,686 sections and 1,440 of 2,766 items, which is the verified subset, not the non-archived one.
2. intelligence_changes: the first policy is parent-gated as above, but the second, `changes_read_authenticated` (roles {public}, so it applies to anon as well, but its test is `auth.role() = 'authenticated' OR 'service_role'`, false for anon), contains no reference to the parent. Policies on a table are OR-ed, so any authenticated user can read EVERY intelligence_changes row, including rows whose parent item is quarantined or archived. anon cannot. The table is empty in practice (0 rows at AT1; written only by src/lib/sources/reconcile.ts under the held change-detection runtime), so the gap is latent, and it would open the moment change detection writes rows for a non-verified item. This policy is one of the three "out-of-band" policies whose production text is in no migration file (drift1 session log line 51), which is why a repo reader would not see it.
