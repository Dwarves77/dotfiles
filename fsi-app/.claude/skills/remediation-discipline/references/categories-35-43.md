### Section 4 — category 36: Date formatting pins its timezone in a hydrated component (a fixed-input value must render identically twice)

On 2026-09-04 the operator's phone-and-desktop measurement of `/regulations` showed a minified React error #418 (hydration mismatch) followed by four cascading `$RS`/`parentNode` errors on first paint. ### Section 4 — category 38: A capped read that claims to fetch "the whole set" pages, it does not lean on a bigger .limit()

[CONFIRMED, live, 2026-09-05] Supabase PostgREST enforces a server-side `db-max-rows=1000` setting: ANY `supabase-js` query without `.range()` paging returns at most 1,000 rows, no matter how large the `.limit(N)` a caller asks for. PERF-13's `getPublicSurfaceSlugs` called the public listings RPC with `.limit(BUILD_TIME_SLUG_ENUM_LIMIT = 20000)` against a live regulations corpus of 1,312+ verified rows; measured on carosledge.com, `[slug]` prerender coverage was a HIT at index 900 and a MISS at 1000/1050/1200/1311 — exactly the first 1,000 rows were ever enumerated, so every route past the 1,000th regulation 404'd or fell back to a client-side render. Root cause: a bigger `.limit(N)` reads as "ask for more" but PostgREST silently truncates the RESPONSE regardless of N — the request succeeds, returns exactly 1,000 rows, and nothing signals truncation. The SAME defect independently produced the obligations register masthead reading "60 of 1000 obligations" against a live 1,141-row table (its "total" was a capped-fetch array's `.length`, not a real count) and a silent per-page drop in `community/directory/page.tsx`'s profiles aggregate past 5,000 rows — three unrelated call sites, one root cause, undiscovered until traced together.

- **A read that means to enumerate an entire table or result set MUST page via `.range()` to genuine exhaustion (the shared `fetchAllRows`/`exactCount` helpers, `src/lib/db/paginate.mjs`) rather than a single request with a larger `.limit(N)`; a displayed "total" MUST come from a DB-computed `{ count: 'exact', head: true }`, never from a capped array's `.length`** — F38 (`unbounded-supabase-read`) fails CI on a new `.limit(<literal>)` call (or a same-file `.limit(<ALL_CAPS_CONST>)` whose declared value) exceeding 1,000 outside its own named, expiring `ALLOWLIST`, and REDS a registered allowlist entry once its named train `expiry` has passed. A read that is genuinely bounded by design (a calibration sample, a small known-size result) stays under 1,000 or is allowlisted with a reason and an expiry train — it is never silently exempted. Invariant RD-63.

### Section 4 — category 39: a PostgREST `.in(col, list)` filter URL-encodes its whole list into the GET request

[CONFIRMED twice, lane INCLAUSE-CLASS, 2026-09-06] A `.in(column, list)` filter is not sent as a request body — `supabase-js`/PostgREST URL-encodes the entire `list` into the GET request's query string. A runtime id list whose size follows the data, not a literal or a provably capped slice, eventually produces a request line long enough that the gateway answers 400 Bad Request or an HTML error page instead of the JSON the caller expects — a different failure shape from category 38's silent row-truncation, because here the REQUEST itself never completes, not the response. Confirmed live twice: review-apply wrappers (run 34045479342, an `.in("id", ids)` call over 911 ids) and `census-off-vertical.mjs` (Maintenance run 34046850770, 1,655 ids, the response body a raw `<!DOCTYPE html>` error page) — in the second case the failure hit only the POST-write read-back, after the chunked write itself had already succeeded; the live table confirmed all 1,655 rows correctly archived despite the read-back's own 400.

- **A `.in(column, list)` call whose `list` is a runtime value (a variable, a property access, a method-chain expression) MUST route through the shared chunking helpers (`readAllByIds`/`guardedUpdateByIds` in `scripts/lib/db.mjs`, or `fetchAllByIdChunks` in `src/lib/db/paginate.mjs` directly for a `.ts` call site) rather than a single `.in()` call sized to the runtime list** — F39 (`unbounded-in-filter`) fails CI on a new `.in()` call whose second argument is not an array literal, a string/template literal, or a SCREAMING_SNAKE_CASE constant, UNLESS the call site is inside one of the chunking implementation files themselves or carries a same-line or preceding-line `// fitness-allow: F39 (reason)` marker stating why the list is actually bounded. Unlike F38, F39 carries no allowlist-with-expiry escape hatch — a site that cannot be proven bounded gets fixed, not allowlisted; a site that IS genuinely bounded by a mechanism the lexical scanner cannot see (an earlier `.limit()`, a request-body length validated upstream, a singleton/per-item/per-user scope) gets its bound stated inline, permanently, at the call site itself. Invariant RD-64.
