### Section 4 — category 27: Primary text is permanent (the document baseline)

The document-level twin of non-destructive grounding. Non-destructive grounding preserves the CLAIM ledger; this preserves the SOURCE DOCUMENT the ledger is grounded against — the full enacted text captured at grounding time, retained so change detection is document-against-document (the ground truth), not ledger-against-ledger (the extraction, one level removed). The operator addendum (2026-07-16): every captured primary is retained permanently, per-capture, immutable.

- **The captured primary text is permanent: a changed re-capture is a new versioned snapshot, never an overwrite of the prior** — `raw_fetches` is APPEND-ONLY by construction, for ANY caller (CC executor or the metered pipeline), because the enforcement lives in the shared capture function `writeSnapshot`: the storage key and the row identity are CONTENT-ADDRESSED (`${source_id}/${day}/${sha256(content)}.html.gz` + `UNIQUE(source_id, content_hash)`, migration 052). A changed re-capture has different bytes, hence a different hash, hence a different key and a different row — it CANNOT overwrite the prior snapshot; an identical re-capture has the same hash, so it is idempotent (one version, `UNIQUE` dedups). There is NO prune or delete path anywhere. This makes the primary baseline immutable and lets a hash-identical re-capture stand as a proof of "unchanged as of [date]." Golden `primary-text-permanent.golden.mjs`. Invariant RD-46.

**Addendum — confidentiality-ruled purges are a sanctioned, narrow exception to append-only (operator ruling 2026-07-18).** RD-46's append-only guarantee protects against SILENT loss of regulatory ground-truth; it was never meant to force permanent retention of a confidential third-party document improperly staged into the corpus by capture-layer error (the NCAER "Logistics Cost in India" incident, `docs/compliance/confidentiality-incident-2026-07-17-ncaer.md` — a disclosure-prohibited report pooled onto an unrelated item, zero claims ever grounded from it). The exception is bounded, not a general erase capability: **(a)** an operator ruling is required EACH time — no standing automatic purge path; **(b)** the evidentiary minimum (source URL, fetch timestamp, byte count, content hash where available, the confidentiality marking quoted verbatim) MUST be captured to a durable `docs/compliance/` incident record BEFORE the purge, never after, so the record substitutes for the content as the permanent evidentiary trace; **(c)** the purge removes only the extractable substance through the guarded write path (never a raw delete) — the row's audit metadata (URL, item association, timestamps) is redacted in place, never removed, so the audit trail survives even though the confidential content does not. A confidentiality-ruled purge is the ONE other sanctioned exit from permanent retention alongside the three sanctioned claim-erasure exits (Section 4 category 26) — it operates one level up, on the captured document rather than the extracted claim, and requires the same proof-before-erasure discipline.

### Section 4 — category 28: Doctrine binds to the pipeline, not the executor (executor-agnostic enforcement)

The build-phase executor (Claude Code driving via Chrome, on subscription, $0) and the steady-state executor (the metered model path) MUST be interchangeable drivers of ONE pipeline — every integrity doctrine binds to the SHARED code both traverse, never to whichever driver is running. If a doctrine were enforced in the executor rather than the pipeline, swapping executors would silently drop it; the enforcement location is therefore audited.

- **Every grounding doctrine binds to the shared pipeline chokepoint, not to the executor: the CC and metered drivers are interchangeable, diverging only at allowlisted skip-points, and the judgment core is driver-blind** — the two drivers meet at `groundBrief` (the single mint chokepoint) and collapse into ONE claim ledger at the extraction pivot (`claims = injected ?? extractClaimLedgerLenient(...)`); after that pivot the data carries no driver identity, only claims. The driver-identity variable is read at EXACTLY three allowlisted points, each the free driver SKIPPING a paid/model step it does not need (acquire-lock skip, extraction source, dominance-guard skip for a deliberate re-source of quarantined junk) — never a difference in JUDGMENT. The judgment core (verbatim kept-filter, mint gates, resolver/tier-stamp, non-destructive `applyLedgerDiff`) contains ZERO driver-identity references and so CANNOT branch on which driver produced the ledger: parity is structural, by construction. Golden `executor-parity.golden.mjs`. Invariant RD-47.

### Section 4 — category 29: A capture must be the item's OWN instrument (target-match verify)

The wrong-instrument class. `officialnessOf` confirms a captured document is AN official instrument; it does NOT confirm it is the CORRECT one for the item. eu_clean_trucking (an item that is the HDV CO2 regulation, Regulation (EU) 2024/1610) captured the CSRD directive (Directive (EU) 2022/2464) and scored "official" — a fact would have ground verbatim against the WRONG law. The gate runs BEFORE extraction, on the shared fetched pool, so both executors inherit it (category 28 / RD-47).

- **A captured primary must be the item's OWN instrument before it grounds: a MISMATCH (the pool bears a different instrument identifier and not this one) is HELD, not ground** — `verifyTargetMatch` / `verifyPoolTargetMatch` (`target-match.mjs`, PURE, reusing `identifier-variants.mjs`) derives the item's own expected instrument identifier (EU CELEX/pair-key or a raw non-EU token) and scans the capture for it. MATCH when the item's own identifier is present (or, absent any identifier signal, subject overlap clears a RAISED threshold — the 0.4 that let eu_clean_trucking slip is gone). MISMATCH — a HARD hold — only when the pool bears a DIFFERENT instrument identifier in a clear instrument context AND the item's own identifier is absent, with no matching block (so it never over-holds when the right instrument is also in the pool, and never hard-holds an item that merely REFERENCES other instruments). UNVERIFIED (no decisive signal) is a SOFT flag: grounding proceeds under the downstream verbatim/floor gates. Golden `target-match.golden.mjs`. Invariant RD-48.

### Section 4 — category 30: Content-gated disposition (label is not proof)

The third-confirmed failure class where a TITLE-LEVEL classification is mistaken for a warrant to act irreversibly. Every archive carries an `archive_reason` LABEL, and the corpus census assigns a Haiku verdict from title + reason + url ONLY — neither ever reads the item's brief. Trusting the label to authorize a bulk delete destroys content: on inspection, 110 of 308 census-`archive_correct` rows were content-bearing, 56 of them carrying grounded facts (UN SDGs/30 claims, DEFRA/28, TxDOT/41, World Bank/20, ITF/12, Blue Visby, the World Bank Carbon Pricing Dashboard). This is the same shape as the Oregon/Polish collision and the o13 press briefing — the label described a source/artifact, the row held real intelligence. The census is TRIAGE, never a warrant.

- **An irreversible disposition executes on content-level emptiness, never on a label: --bucket refuses non-allowlist reasons, --empty-only requires brief_len=0 AND zero claims, tombstone precedes delete** — the ONE disposition vehicle (`scripts/_reground/tombstone-delete.mjs`) bakes the gate into the tool, not the operator's trust: a `--bucket` outside the deletable-reason allowlist (content-survives / duplicate / pure-artifact only — `off_vertical` / `non_regulatory_source` / `Superseded` / `Repealed` are excluded: never delete accurate data) is REFUSED; `--empty-only` filters every candidate to `brief_len=0` AND zero grounded claims (`section_claim_provenance`) BEFORE deletion, so a content-bearing row is removed from targets and routed to per-item review; and the tombstone (`disposition_ledger`) is written BEFORE the guarded delete (fail-closed). Golden `disposition-content-gate.golden.mjs` (structural, 18/18). Doctrine `label-is-not-proof`; invariant RD-42. Proven live 2026-07-17: 198 verified-disposition removals, 198 tombstones, archived 419→221, zero live item touched.

- **Second-order addendum — content-is-not-nature (the RESTORE judgment is item-vs-source, and it is NOT mechanizable).** A mechanical content floor (brief present, claims real) is NECESSARY but NOT SUFFICIENT to restore a wrongly-archived row: it cannot tell whether the content CONSTITUTES an intelligence item or merely DESCRIBES a source. The discriminator (freight-customer intelligence test): RESTORE a named regulation / standard / framework / program / finding with decision value; CONFIRM-archive an access point / publisher / portal / register / org-overview (its content survives as the source row the reclassification correctly created — EUR-Lex-the-database is the archetype). Group-③ borderlines: a research org / industry body restores ONLY if the row carries a specific finding / standard / position with freight value (an org's existence or mission is source-shaped); a news outlet is presumptively source-shaped absent a specific covered finding whose value survives without the outlet; an agency environmental PAGE is source-shaped, an agency PROGRAM with obligations or incentives is an item. This discrimination is JUDGMENT and stays in the review lane PERMANENTLY — never mechanized. `label-is-not-proof` binds OPERATOR labels too: the operator-named "DEFRA" RESTORE presumption was overridden by the content read (row is "UK DEFRA: Organizational Overview" — source-shaped) and CONFIRM-archived on evidence. Group-② tombstone rule: a confirm-archive is tombstone-deleted ONLY where its source row verifiably exists AND is active; anything whose source row is missing registers the source first or HOLDS — content must survive somewhere before the item stops being the place it survives. RESTORE also carries a jurisdiction-code check (the CO/Colombia, US-ID/Indonesia collision class — the sweep is the cheapest moment to catch mis-coded states).

### Section 4 — category 31: Harness-run integrity (an iterated harness's own run history is a class fix target too)

The self-referential case of this skill's own principle. A harness that iterates — the mint kit, the screen rules, the fetch-drain ladder — accumulates a run history the SAME way any other system accumulates state, and that history is subject to the SAME failure modes this skill exists to close everywhere else. Round 1 of the screen harness (12 title rules, 3,661 rows, 349 decided) had its own raw per-row output silently overwritten by round 2's run against the identical fixed `--out-basename`, because the runner wrote to a fixed path rather than a run-numbered one; all that survives today is an aggregate count in a commit message and a session-log addendum — a summary standing in for a lost full trace, the exact class arXiv 2603.28052's ablation measured as WORSE than no trace at all. A harness whose own behavior changes (a new rule, a fixed validator criterion) without a run recording what changed and why is the same silent-drift class category 21 names for a dormant module, applied to a harness's own history instead of its code.

- **Every harness-run artifact validates against its schema, every registered harness family has at least one recorded run, and a harness family's governing files MUST NOT drift from the harness_version its recorded runs name without EITHER a newer run or a pending-run marker recording the change and the run that will supersede it** — `writeRunArtifact`/`readRunHistory`/`hashHarnessVersion` (`scripts/lib/run-artifact.mjs`, Wave MH-1) enforce the artifact shape fail-closed on write; F28 (`harness-run-integrity`, Wave MH-2) enforces the rest against the committed tree: every family directory under `scripts/harness-runs/` has ≥1 valid artifact, and each family's governing files (named in `scripts/harness-runs/CONVENTION.md`'s `harness_version` hash table) re-hash to a value some artifact in that family already recorded, or the drift is acknowledged by a `PENDING-RUN.md` naming what changed and the run that will close it — itself reverse-audited so the marker cannot become a permanent exemption once the run lands. A family with ≥2 artifacts additionally carries a `LAST-PROPOSER-PASS.md` naming its latest run — the machine-checkable half of the "no harness runs its next batch until a proposer has read the full prior record" precondition (`PROPOSER-RUNBOOK.md`). Invariant RD-55.

### Section 4 — category 32: Propagation engine gates (a computed value's pollution barrier and a statutory formula's purity are class fix targets, not per-caller trust)

The propagation engine (`docs/specs/08-flywheel-design.md` §2-§5, Lane DP-ENGINE) computes and invalidates derived figures at scale — the same "one path, mechanically enforced" principle this skill applies everywhere else, applied to a value's ADMISSIBILITY (may this figure be shown/analysed/calculated-with/filed) and to a statutory formula's INPUT PURITY (a legally-prescribed number must never quietly absorb a model's guess). Trusting each caller to remember the gate is the same honor-system failure category 9's producer-consumer orphan and category 21's dormant-capability class both name for a different surface.

- **Nothing outside `src/lib/propagation/` MUST read the raw `derived_values` table directly — every consumer reads through `derived_values_admissible` (RLS-granted) or calls `admissibleFor()` (the pollution barrier)** — migration 285 denies raw-table SELECT via RLS and grants only the view; F31 (`derived-values-gate`) backstops a service-role client (which bypasses RLS entirely) from slipping past that gate in code, failing CI on a literal `.from("derived_values")` call site anywhere outside the one directory that owns this read path. Invariant RD-56.

- **A statutory computation's declared inputs MUST NOT cite a live `estimated_values` row or a `derived_values` row whose derivation is modelled/estimated/interpolated — a legally-prescribed figure never quietly absorbs a model's guess** — migration 286's `assert_statutory_purity()` trigger enforces this at write time (proven live by that migration's own self-check); F32 (`statutory-purity`) backstops the trigger's continued presence in the repository copy of the migration and ships a tested, pure JS mirror (`assertStatutoryPurity`) a future JS-side writer can call pre-flight. Invariant RD-57.
